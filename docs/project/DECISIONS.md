## ADR-001 — Инициализация GitHub-репозитория

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Проекту нужен публичный VCS-хостинг для родительской папки `TBHStats`. Внутри неё лежит вложенная папка `claude-code-orchestrator-kit/` — это самостоятельный пакет со своим апстримом и собственной git-историей, который не должен попадать в репозиторий проекта.

**Решение**: Создан публичный репозиторий `AlgorithmicTrade/TBHStats` для родительской папки. Вложенный `claude-code-orchestrator-kit` исключён из индекса через `.gitignore`.

**Альтернативы / почему отклонены**:
- **git submodule** — отклонён: добавляет связанность с апстримом и усложняет клонирование/обновление; для текущей задачи (просто не версионировать чужой пакет) избыточен.
- **Vendoring (вкомитить копию пакета)** — отклонён: дублирует чужую историю в нашем репозитории и создаёт риск рассинхронизации с апстримом.

**Последствия**: Репозиторий содержит только код проекта; чужой пакет остаётся локальным инструментом и не засоряет историю. Все git/npm/release-команды для kit выполняются из его собственной папки (см. корневой `CLAUDE.md`).

## ADR-002 — Технологический стек: .NET 8 / C# / WinUI 3

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужен нативный десктоп-виджет для Windows 11, который надёжно захватывает окно стороннего GPU-приложения (даже перекрытое), делает OCR и хранит локальную историю. Дополнительно — задел под будущий Android-клиент.

**Решение**: Стек — **.NET 8 (LTS) / C# 12 / WinUI 3** (Windows App SDK). **WPF** зафиксирован как fallback для оверлей-оболочки, если прозрачность/`Topmost` в WinUI 3 окажутся проблемными.

**Альтернативы / почему отклонены**:
- **Tauri (React/TS + Rust)** — отклонён: два языка в стеке, выше когнитивная нагрузка; нативная интеграция с Win11-API менее прямая.
- **Electron (всё на TS)** — отклонён: хрупкий захват перекрытого окна, тяжёлый рантайм, высокое потребление ресурсов для лёгкого виджета.

**Причина выбора**: лучшая нативная интеграция с Windows 11 (прямой доступ к WinRT — WGC/OCR), один язык/рантайм на весь стек и реальный задел под Android через .NET MAUI с переиспользованием доменного ядра.

**Последствия**: Доступ к WGC/Windows.Media.Ocr через CsWinRT-проекции; целевой TFM уровня `net8.0-windows10.0.22621.0`. Доменное ядро `TBHStats.Core` остаётся без UI/WinRT-зависимостей ради переиспользования в MAUI (см. ADR-010).

## ADR-003 — Адаптация конституции под .NET (v2.0.0 → v2.1.0)

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Конституция проекта (`.specify/memory/constitution.md`) в версии 2.0.0 формулировала Принцип V «Strict Type Safety» в терминах TypeScript strict. Выбранный стек — C#/.NET (ADR-002), поэтому требование к типобезопасности нужно переориентировать, не ослабляя его.

**Решение**: Конституция обновлена до **v2.1.0**. Принцип V перенацелен с TypeScript strict на **C#/.NET strict**: включённые nullable reference types (`<Nullable>enable</Nullable>`), запрет `dynamic`, warnings-as-errors по nullability на доменных проектах, чистый прогон analyzers и обязательный `dotnet build` до коммита. Конкретизированы разделы Technology Standards, Accessibility, Security, File Organization.

**Альтернативы / почему отклонены**:
- **Оставить формулировку про TypeScript и трактовать «по духу»** — отклонено: создавало бы конфликт между гейтом конституции и реальным стеком, провоцируя обход гейта.

**Легитимность**: Поправка принята как штатное изменение конституции (Amendment Procedure: задокументированная причина + impact-анализ + version bump + Sync Impact Report) **с согласия пользователя**, а не как обход quality-гейта. Bump MINOR — изменение аддитивно-уточняющее (re-target принципа, конкретизация плейсхолдеров), без слома существующих требований.

**Последствия**: Constitution Check в `plan.md` проходит без нарушений; «конфликт TypeScript vs C#» снят легитимно. Все последующие фичи оцениваются против v2.1.0.

## ADR-004 — Способ захвата окна: Windows.Graphics.Capture по HWND

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Помощник должен считывать содержимое окна игры, оставаясь устойчивым к перекрытию другими окнами и следуя за окном при перемещении/ресайзе/переносе на другой монитор (FR-005, FR-005b). Прямой записи в память игры нет (observe-only).

**Решение**: **Windows.Graphics.Capture (WGC)** с таргетингом по **HWND** через interop (`IGraphicsCaptureItemInterop.CreateForWindow`). WGC отдаёт GPU-текстуру конкретного окна, захватывает его даже в фоне/при перекрытии и автоматически следует за окном.

**Альтернативы / почему отклонены**:
- **PrintWindow (GDI, `PW_RENDERFULLCONTENT`)** — отклонён как основной путь: у GPU-ускоренных приложений часто отдаёт чёрный кадр. Оставлен как аварийный **fallback**.
- **BitBlt со скриншота экрана** — отклонён: ломается при перекрытии и привязан к экрану, а не к окну (противоречит FR-005/005b).
- **DXGI Desktop Duplication** — отклонён: захватывает весь экран/монитор, а не конкретное окно.

**Последствия**: «Ожидание вместо ошибки» остаётся релевантным только для свёрнутого/закрытого окна (`IsIconic` → нет валидной поверхности). Захват по HWND — фундамент привязки ROI к окну (ADR-006). Встроенный WinRT-API, без сторонних зависимостей.

## ADR-005 — Движок OCR: Windows.Media.Ocr (+ Tesseract fallback)

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: С захваченного кадра нужно распознавать игровые числа (включая сокращённый формат 1.2K/3.4M) и текст (названия вкладок). Предпочтение — встроенным платформенным API без тяжёлых зависимостей (Принцип III).

**Решение**: Основной движок — **Windows.Media.Ocr** (встроен в Windows, 0 сторонних зависимостей, принимает `SoftwareBitmap` напрямую из WGC, возвращает слова с bounding box). **Tesseract** — fallback для «трудных» ROI, где точность встроенного движка недостаточна (настраивается под цифры через `tessedit_char_whitelist`).

**Альтернативы / почему отклонены**:
- **PaddleOCR / Surya** — отклонены: тяжёлый рантайм (Python/ONNX), избыточны для коротких числовых строк.

**Последствия**: Фактическая точность на конкретном шрифте игры — эмпирический риск, проверяется на реальных скриншотах в `Capture.Tests`. Митигировано confidence-порогом + sanity-проверками значений и per-ROI выбором движка через конфиг.

## ADR-006 — ROI как нормализованные доли клиентской области окна

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Области считывания (ROI) должны оставаться корректными при любом положении/размере/масштабе окна, на любом мониторе и при любом DPI рабочего стола (FR-005b), без ручной перекалибровки.

**Решение**: ROI хранятся как **нормализованные доли клиентской области окна** (`x, y, w, h ∈ [0..1]`), а не как пиксели экрана. На каждом кадре известен размер клиентской области (из WGC item size) → доли разворачиваются в пиксели текущего кадра. Калибровка пользователем = разметка прямоугольников поверх захваченного кадра, сохраняемая в долях.

**Альтернативы / почему отклонены**:
- **Абсолютные экранные координаты** — отклонены: ломаются при любом перемещении/масштабировании/смене монитора.

**Последствия**: Независимость от конфигурации системы и расположения окна достигается «бесплатно» поверх захвата по HWND (ADR-004). Логика маппинга — тонкая доменная математика в `TBHStats.Capture/Roi`.

## ADR-007 — Выбираемая пользователем цель оптимизации

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Главная аналитическая ценность — рекомендация оптимального этапа для фарма. Игрок может фармить ради разных целей (золото или опыт), и одной фиксированной метрики недостаточно.

**Решение**: Цель оптимизации **выбирается пользователем — золото/час ИЛИ опыт/час** (по умолчанию — **золото/час**). Переключение цели пересчитывает ранжирование этапов и рекомендацию (FR-009/FR-019). Сундуки учитываются и показываются (сундуки/час, количество за забег), но **не являются целью оптимизации в v1**.

**Альтернативы / почему отклонены**:
- **Единственная фиксированная метрика** — отклонена: не покрывает разные стратегии фарма.
- **Сделать сундуки целью оптимизации в v1** — отклонено: усложняет ранжирование без подтверждённой ценности; отложено за пределы v1.

**Последствия**: В модели появляется `Optimization Profile` (выбранная цель). Ранжирование и рекомендация параметризуются профилем; сундуки остаются информационным показателем.

## ADR-008 — Корректировка матрицы этапов: 60, а не 90

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: В первичном описании структура контента указывалась как 3 акта × **3 сложности** × 10 этапов = 90 этапов. По уточнению пользователя (2026-05-31) сложностей в игре **две** (Normal, Nightmare).

**Решение**: Матрица этапов скорректирована до **3 акта × 2 сложности × 10 этапов = 60 этапов**. Обозначение «акт-этап» (1-1 … 3-10) с разделением по сложности.

**Альтернативы / почему отклонены**:
- **Оставить 90 (3 сложности)** — отклонено: фактически неверно, противоречит уточнению пользователя.

**Последствия**: Все агрегаты, экран сравнения и success-критерии оперируют 60 этапами. Один и тот же номер этапа на разных актах/сложностях — разные сущности (данные не смешиваются). Модель остаётся расширяемой под будущие сложности/акты (см. ADR-009).

## ADR-009 — Расширяемость через декларативный GameMechanicsConfig

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Контент игры будет меняться (новые типы сундуков, классы героя, акты/сложности/этапы, вкладки). Добавление таких элементов не должно требовать переработки архитектуры или ломать накопленную историю (FR-021, SC-010).

**Решение**: Учитываемые сущности описываются **декларативным GameMechanicsConfig** (типы сундуков, классы, акты/сложности/этапы, вкладки) в `TBHStats.Core/Mechanics` — встроенный default с возможностью переопределения из файла/БД. Справочные сущности (ChestType, Class и т.п.) — данные-записи, а **не enum'ы-в-коде**. Новый элемент = запись в конфиге + ROI в калибровке + привязка к источнику, без правки доменных типов и схемы БД.

**Альтернативы / почему отклонены**:
- **Жёстко зашитые enum'ы / захардкоженные списки** — отклонены: любое расширение требует правки кода и схемы, рискует инвалидировать историю.

**Последствия**: Расширение идёт данными, не кодом. История остаётся валидной, т.к. ссылается на справочные id, а не на захардкоженные значения. Прямое выполнение FR-021/SC-010.

## ADR-010 — Android вне v1: Core без UI и контракт Remote API как задел

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: В будущем планируется Android-клиент для удалённого просмотра статистики (FR-020), но в v1 он вне объёма. При этом архитектура v1 не должна мешать будущему переиспользованию логики.

**Решение**: Вся не-UI доменная логика выносится в **`TBHStats.Core` без UI/WinRT-зависимостей** → переиспользуема в **.NET MAUI**. Контракт **Remote API** (OpenAPI) зафиксирован как задел: будущий локальный сервер (`TBHStats.Remote`, ASP.NET minimal API) привязан к **localhost/LAN + парный токен**. В v1 создаются только границы (интерфейсы репозиториев/DTO); сам сервер не поднимается.

**Альтернативы / почему отклонены**:
- **Не закладывать границы и спроектировать переиспязуемость потом** — отклонено: риск «протекания» UI/WinRT-зависимостей в доменное ядро, что заблокировало бы MAUI-переиспользование.

**Последствия**: `TBHStats.Remote` — пустой задел в решении, в v1 не реализуется. Безопасность будущего канала (аутентификация парным токеном, привязка к localhost/LAN) закреплена в конституции (Security). Данные хранятся так, чтобы их мог отдать будущий API.

## ADR-011 — Учёт сундуков по транзиентным точкам MainZone

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Полученные сундуки отображаются в основной зоне (MainZone) как заполняемые «точки» под иконкой каждого типа. Счётчик **транзиентный**: растёт при выпадении и падает к 0 при открытии сундука. Наивный «прирост = текущее − предыдущее» трактовал бы открытие сундука как потерю.

**Решение**: «Получено сундуков за забег» = **сумма положительных приростов** счётчика точек MainZone по каждому типу. Падение счётчика к 0 (открытие сундука) трактуется как **открытие, а НЕ потеря** и не уменьшает накопленный итог забега. Накопленный итог забега неубывает.

**Альтернативы / почему отклонены**:
- **Считать дельту как «текущее − предыдущее» без разделения знака** — отклонено: обнуление при открытии ломало бы подсчёт «получено за забег».

**Последствия**: Логика подсчёта сундуков — чисто доменная (`TBHStats.Core/Parsing`), покрыта unit-тестами на реальных строках. Согласуется с confidence-фильтром: недостоверные точки не записываются.

## ADR-012 — Детекция завершения этапа по прогрессбару/боссу

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужен надёжный сигнал момента завершения этапа для фиксации `stageTime` и закрытия `StageRun`. Угадывание по сбросу/изменению числовых значений хрупко (множество ложных причин сброса).

**Решение**: Завершение этапа детектируется по **прогрессбару прохождения в MainZone**: в конце полоски появляется **босс этапа**, убийство которого = прохождение этапа. Это сигнал сегментации забегов. Дополнительно: босс этапа ↔ синий сундук; босс акта (этап «-10») ↔ красный сундук.

**Альтернативы / почему отклонены**:
- **Угадывание завершения по сбросу/обнулению числовых значений** — отклонено как менее надёжное: легко спутать с артефактами OCR, level-up'ом или открытием сундука.

**Последствия**: `StageRun` закрывается по явному событию (босс убит), а не по эвристике значений. Корректная сегментация забегов питает агрегаты этапов (FR-007/FR-008) и интерпретацию темпа сундуков.

## ADR-013 — Хранилище: SQLite + EF Core

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужна локальная персистентность истории забегов и агрегатов, переживающая перезапуск/перезагрузку (FR-011), с расширяемой схемой под новые механики без потери истории (FR-013/FR-021) и LINQ-агрегациями по этапам (FR-008).

**Решение**: **SQLite через EF Core** (`Microsoft.EntityFrameworkCore.Sqlite`), файл в `%LOCALAPPDATA%\TBHStats\tbhstats.db`. EF Core даёт миграции (расширение схемы без потери истории), LINQ-агрегации и nullable-аннотации (Принцип V). Конфиг механик — отдельная таблица + сидинг из декларативного описания (см. ADR-009).

**Альтернативы / почему отклонены**:
- **LiteDB** — отклонён: слабее по миграциям и агрегации для растущей истории.
- **Сырой JSON-файл** — отклонён: нет индексов и конкурентной записи, плохо масштабируется на историю в тысячи записей.

**Последствия**: Тесты `Data` идут на **реальном временном SQLite-файле** (не in-memory-мок) — проверяется реальная SQL-семантика. Объём (тысячи `StageRun`) для SQLite тривиален.

## ADR-014 — Графики: LiveCharts2

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Для трендов (FR-018, приоритет P3) нужны интерактивные графики (тултипы по точкам) с поддержкой WinUI 3 и переиспользуемостью под будущий MAUI-клиент.

**Решение**: **LiveCharts2** (`LiveChartsCore.SkiaSharpView.WinUI`) — официальная поддержка WinUI 3, единственная зависимость SkiaSharp, качественные анимации/интерактивность, единый API на все .NET UI.

**Альтернативы / почему отклонены**:
- **ScottPlot** — не отклонён жёстко: отличен для плотных/научных данных и быстр, но под лёгкий интерактивный виджет LiveCharts2 удобнее по стилизации/тултипам. Держится как **запасной вариант** при проблемах Skia-рендера в оверлее.

**Последствия**: Графики — фича P3 (после P1 живых метрик и P2 истории/рекомендаций). Изоляция UI-оболочки за тонким интерфейсом позволяет при необходимости заменить чарт-библиотеку без влияния на Core/Capture/Data.

## ADR-015 — UI-тесты живой игры: FlaUI + визуальная локализация, не Playwright

**Дата**: 2026-05-31 · **Статус**: Accepted

**Контекст**: требуется набор «нехрупких» детерминированных UI-тестов поверх реально запущенной игры — харнесс сам аудирует интерфейс, навигирует по разделам человекоподобными кликами, проверяет детекцию разделов и чтение значений (FR-022…FR-027).

**Решение**: отдельный QA-проект `TBHStats.UiTests` на **xUnit + FlaUI** (UIA + нативный ввод) + **визуальная локализация элементов** (OCR названий через переиспользование `TBHStats.Capture`) + **инъекция кликов SendInput** (случайная точка в границах элемента, случайная задержка, easing). Сценарии — в `ui-test-scenarios.md` (TS-00…TS-10). Harness НЕ входит в поставку; продукт остаётся observe-only.

**Альтернативы/почему отклонены**:
- **Playwright** — браузерный инструмент; TBH — нативный десктоп (нет API, рендер на canvas/DirectX, UIA-дерево обычно недоступно). Применим только если игра окажется Electron с CDP (проверяется в TS-00) — не базовый путь.
- **WinAppDriver/Appium** — слабо поддерживается; FlaUI активнее и роднее для .NET.
- Чисто пиксельные клики — хрупкие; заменены на ассерты по распознанному состоянию + ожидания.

**Безопасность**: потребовался **carve-out конституции (v2.1.0 → v2.2.0)** — продукт observe-only, но QA-харнесс может инжектить ввод только в тест-режиме, с Safety-Guard (запрет необратимых действий: Runes/Cube/Stash/Trade).

**Последствия**: harness переиспользует продуктовый слой распознавания (двойная выгода — заодно валидирует Capture/детекцию). Эмпирический пункт: тип приложения TBH (нативное/Electron) определяется в TS-00, влияет лишь на наличие альтернативного CDP-пути.
