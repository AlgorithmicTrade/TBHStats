## ADR-001 — Инициализация GitHub-репозитория

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Проекту нужен публичный VCS-хостинг для родительской папки `TBHStats`. Внутри неё лежит вложенная папка `claude-code-orchestrator-kit/` — это самостоятельный пакет со своим апстримом и собственной git-историей, который не должен попадать в репозиторий проекта.

**Решение**: Создан публичный репозиторий `AlgorithmicTrade/TBHStats` для родительской папки. Вложенный `claude-code-orchestrator-kit` исключён из индекса через `.gitignore`.

**Альтернативы / почему отклонены**:
- **git submodule** — отклонён: добавляет связанность с апстримом и усложняет клонирование/обновление; для текущей задачи (просто не версионировать чужой пакет) избыточен.
- **Vendoring (вкомитить копию пакета)** — отклонён: дублирует чужую историю в нашем репозитории и создаёт риск рассинхронизации с апстримом.

**Последствия**: Репозиторий содержит только код проекта; чужой пакет остаётся локальным инструментом и не засоряет историю. Все git/npm/release-команды для kit выполняются из его собственной папки (см. корневой `CLAUDE.md`).

## ADR-002 — Технологический стек: .NET 8 / C# / WinUI 3

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужен нативный десктоп-виджет для Windows 11, который надёжно захватывает окно стороннего GPU-приложения (даже перекрытое), делает OCR и хранит локальную историю. Дополнительно — задел под будущий Android-клиент.

**Решение**: Стек — **.NET 8 (LTS) / C# 12 / WinUI 3** (Windows App SDK). **WPF** зафиксирован как fallback для оверлей-оболочки, если прозрачность/`Topmost` в WinUI 3 окажутся проблемными.

**Альтернативы / почему отклонены**:
- **Tauri (React/TS + Rust)** — отклонён: два языка в стеке, выше когнитивная нагрузка; нативная интеграция с Win11-API менее прямая.
- **Electron (всё на TS)** — отклонён: хрупкий захват перекрытого окна, тяжёлый рантайм, высокое потребление ресурсов для лёгкого виджета.

**Причина выбора**: лучшая нативная интеграция с Windows 11 (прямой доступ к WinRT — WGC/OCR), один язык/рантайм на весь стек и реальный задел под Android через .NET MAUI с переиспользованием доменного ядра.

**Последствия**: Доступ к WGC/Windows.Media.Ocr через CsWinRT-проекции; целевой TFM уровня `net8.0-windows10.0.22621.0`. Доменное ядро `TBHStats.Core` остаётся без UI/WinRT-зависимостей ради переиспользования в MAUI (см. ADR-010).

## ADR-003 — Адаптация конституции под .NET (v2.0.0 → v2.1.0)

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Конституция проекта (`.specify/memory/constitution.md`) в версии 2.0.0 формулировала Принцип V «Strict Type Safety» в терминах TypeScript strict. Выбранный стек — C#/.NET (ADR-002), поэтому требование к типобезопасности нужно переориентировать, не ослабляя его.

**Решение**: Конституция обновлена до **v2.1.0**. Принцип V перенацелен с TypeScript strict на **C#/.NET strict**: включённые nullable reference types (`<Nullable>enable</Nullable>`), запрет `dynamic`, warnings-as-errors по nullability на доменных проектах, чистый прогон analyzers и обязательный `dotnet build` до коммита. Конкретизированы разделы Technology Standards, Accessibility, Security, File Organization.

**Альтернативы / почему отклонены**:
- **Оставить формулировку про TypeScript и трактовать «по духу»** — отклонено: создавало бы конфликт между гейтом конституции и реальным стеком, провоцируя обход гейта.

**Легитимность**: Поправка принята как штатное изменение конституции (Amendment Procedure: задокументированная причина + impact-анализ + version bump + Sync Impact Report) **с согласия пользователя**, а не как обход quality-гейта. Bump MINOR — изменение аддитивно-уточняющее (re-target принципа, конкретизация плейсхолдеров), без слома существующих требований.

**Последствия**: Constitution Check в `plan.md` проходит без нарушений; «конфликт TypeScript vs C#» снят легитимно. Все последующие фичи оцениваются против v2.1.0.

## ADR-004 — Способ захвата окна: Windows.Graphics.Capture по HWND

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Помощник должен считывать содержимое окна игры, оставаясь устойчивым к перекрытию другими окнами и следуя за окном при перемещении/ресайзе/переносе на другой монитор (FR-005, FR-005b). Прямой записи в память игры нет (observe-only).

**Решение**: **Windows.Graphics.Capture (WGC)** с таргетингом по **HWND** через interop (`IGraphicsCaptureItemInterop.CreateForWindow`). WGC отдаёт GPU-текстуру конкретного окна, захватывает его даже в фоне/при перекрытии и автоматически следует за окном.

**Альтернативы / почему отклонены**:
- **PrintWindow (GDI, `PW_RENDERFULLCONTENT`)** — отклонён как основной путь: у GPU-ускоренных приложений часто отдаёт чёрный кадр. Оставлен как аварийный **fallback**.
- **BitBlt со скриншота экрана** — отклонён: ломается при перекрытии и привязан к экрану, а не к окну (противоречит FR-005/005b).
- **DXGI Desktop Duplication** — отклонён: захватывает весь экран/монитор, а не конкретное окно.

**Последствия**: «Ожидание вместо ошибки» остаётся релевантным только для свёрнутого/закрытого окна (`IsIconic` → нет валидной поверхности). Захват по HWND — фундамент привязки ROI к окну (ADR-006). Встроенный WinRT-API, без сторонних зависимостей.

## ADR-005 — Движок OCR: Windows.Media.Ocr (+ Tesseract fallback)

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: С захваченного кадра нужно распознавать игровые числа (включая сокращённый формат 1.2K/3.4M) и текст (названия вкладок). Предпочтение — встроенным платформенным API без тяжёлых зависимостей (Принцип III).

**Решение**: Основной движок — **Windows.Media.Ocr** (встроен в Windows, 0 сторонних зависимостей, принимает `SoftwareBitmap` напрямую из WGC, возвращает слова с bounding box). **Tesseract** — fallback для «трудных» ROI, где точность встроенного движка недостаточна (настраивается под цифры через `tessedit_char_whitelist`).

**Альтернативы / почему отклонены**:
- **PaddleOCR / Surya** — отклонены: тяжёлый рантайм (Python/ONNX), избыточны для коротких числовых строк.

**Последствия**: Фактическая точность на конкретном шрифте игры — эмпирический риск, проверяется на реальных скриншотах в `Capture.Tests`. Митигировано confidence-порогом + sanity-проверками значений и per-ROI выбором движка через конфиг.

## ADR-006 — ROI как нормализованные доли клиентской области окна

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Области считывания (ROI) должны оставаться корректными при любом положении/размере/масштабе окна, на любом мониторе и при любом DPI рабочего стола (FR-005b), без ручной перекалибровки.

**Решение**: ROI хранятся как **нормализованные доли клиентской области окна** (`x, y, w, h ∈ [0..1]`), а не как пиксели экрана. На каждом кадре известен размер клиентской области (из WGC item size) → доли разворачиваются в пиксели текущего кадра. Калибровка пользователем = разметка прямоугольников поверх захваченного кадра, сохраняемая в долях.

**Альтернативы / почему отклонены**:
- **Абсолютные экранные координаты** — отклонены: ломаются при любом перемещении/масштабировании/смене монитора.

**Последствия**: Независимость от конфигурации системы и расположения окна достигается «бесплатно» поверх захвата по HWND (ADR-004). Логика маппинга — тонкая доменная математика в `TBHStats.Capture/Roi`.

## ADR-007 — Выбираемая пользователем цель оптимизации

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Главная аналитическая ценность — рекомендация оптимального этапа для фарма. Игрок может фармить ради разных целей (золото или опыт), и одной фиксированной метрики недостаточно.

**Решение**: Цель оптимизации **выбирается пользователем — золото/час ИЛИ опыт/час** (по умолчанию — **золото/час**). Переключение цели пересчитывает ранжирование этапов и рекомендацию (FR-009/FR-019). Сундуки учитываются и показываются (сундуки/час, количество за забег), но **не являются целью оптимизации в v1**.

**Альтернативы / почему отклонены**:
- **Единственная фиксированная метрика** — отклонена: не покрывает разные стратегии фарма.
- **Сделать сундуки целью оптимизации в v1** — отклонено: усложняет ранжирование без подтверждённой ценности; отложено за пределы v1.

**Последствия**: В модели появляется `Optimization Profile` (выбранная цель). Ранжирование и рекомендация параметризуются профилем; сундуки остаются информационным показателем.

## ADR-008 — Корректировка матрицы этапов: 60, а не 90

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: В первичном описании структура контента указывалась как 3 акта × **3 сложности** × 10 этапов = 90 этапов. По уточнению пользователя (2026-05-31) сложностей в игре **две** (Normal, Nightmare).

**Решение**: Матрица этапов скорректирована до **3 акта × 2 сложности × 10 этапов = 60 этапов**. Обозначение «акт-этап» (1-1 … 3-10) с разделением по сложности.

**Альтернативы / почему отклонены**:
- **Оставить 90 (3 сложности)** — отклонено: фактически неверно, противоречит уточнению пользователя.

**Последствия**: Все агрегаты, экран сравнения и success-критерии оперируют 60 этапами. Один и тот же номер этапа на разных актах/сложностях — разные сущности (данные не смешиваются). Модель остаётся расширяемой под будущие сложности/акты (см. ADR-009).

## ADR-009 — Расширяемость через декларативный GameMechanicsConfig

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Контент игры будет меняться (новые типы сундуков, классы героя, акты/сложности/этапы, вкладки). Добавление таких элементов не должно требовать переработки архитектуры или ломать накопленную историю (FR-021, SC-010).

**Решение**: Учитываемые сущности описываются **декларативным GameMechanicsConfig** (типы сундуков, классы, акты/сложности/этапы, вкладки) в `TBHStats.Core/Mechanics` — встроенный default с возможностью переопределения из файла/БД. Справочные сущности (ChestType, Class и т.п.) — данные-записи, а **не enum'ы-в-коде**. Новый элемент = запись в конфиге + ROI в калибровке + привязка к источнику, без правки доменных типов и схемы БД.

**Альтернативы / почему отклонены**:
- **Жёстко зашитые enum'ы / захардкоженные списки** — отклонены: любое расширение требует правки кода и схемы, рискует инвалидировать историю.

**Последствия**: Расширение идёт данными, не кодом. История остаётся валидной, т.к. ссылается на справочные id, а не на захардкоженные значения. Прямое выполнение FR-021/SC-010.

## ADR-010 — Android вне v1: Core без UI и контракт Remote API как задел

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: В будущем планируется Android-клиент для удалённого просмотра статистики (FR-020), но в v1 он вне объёма. При этом архитектура v1 не должна мешать будущему переиспользованию логики.

**Решение**: Вся не-UI доменная логика выносится в **`TBHStats.Core` без UI/WinRT-зависимостей** → переиспользуема в **.NET MAUI**. Контракт **Remote API** (OpenAPI) зафиксирован как задел: будущий локальный сервер (`TBHStats.Remote`, ASP.NET minimal API) привязан к **localhost/LAN + парный токен**. В v1 создаются только границы (интерфейсы репозиториев/DTO); сам сервер не поднимается.

**Альтернативы / почему отклонены**:
- **Не закладывать границы и спроектировать переиспязуемость потом** — отклонено: риск «протекания» UI/WinRT-зависимостей в доменное ядро, что заблокировало бы MAUI-переиспользование.

**Последствия**: `TBHStats.Remote` — пустой задел в решении, в v1 не реализуется. Безопасность будущего канала (аутентификация парным токеном, привязка к localhost/LAN) закреплена в конституции (Security). Данные хранятся так, чтобы их мог отдать будущий API.

## ADR-011 — Учёт сундуков по транзиентным точкам MainZone

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Полученные сундуки отображаются в основной зоне (MainZone) как заполняемые «точки» под иконкой каждого типа. Счётчик **транзиентный**: растёт при выпадении и падает к 0 при открытии сундука. Наивный «прирост = текущее − предыдущее» трактовал бы открытие сундука как потерю.

**Решение**: «Получено сундуков за забег» = **сумма положительных приростов** счётчика точек MainZone по каждому типу. Падение счётчика к 0 (открытие сундука) трактуется как **открытие, а НЕ потеря** и не уменьшает накопленный итог забега. Накопленный итог забега неубывает.

**Альтернативы / почему отклонены**:
- **Считать дельту как «текущее − предыдущее» без разделения знака** — отклонено: обнуление при открытии ломало бы подсчёт «получено за забег».

**Последствия**: Логика подсчёта сундуков — чисто доменная (`TBHStats.Core/Parsing`), покрыта unit-тестами на реальных строках. Согласуется с confidence-фильтром: недостоверные точки не записываются. Уточнено в **ADR-018**: иконка типа имеет до трёх позиций по числу присутствующих типов `N`; какие точки какому типу принадлежат в текущей раскладке определяет `IChestLayoutResolver` до применения логики «сумма положительных приростов».

## ADR-012 — Детекция завершения этапа по прогрессбару/боссу

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужен надёжный сигнал момента завершения этапа для фиксации `stageTime` и закрытия `StageRun`. Угадывание по сбросу/изменению числовых значений хрупко (множество ложных причин сброса).

**Решение**: Завершение этапа детектируется по **прогрессбару прохождения в MainZone**: в конце полоски появляется **босс этапа**, убийство которого = прохождение этапа. Это сигнал сегментации забегов. Дополнительно: босс этапа ↔ синий сундук; босс акта (этап «-10») ↔ красный сундук.

**Альтернативы / почему отклонены**:
- **Угадывание завершения по сбросу/обнулению числовых значений** — отклонено как менее надёжное: легко спутать с артефактами OCR, level-up'ом или открытием сундука.

**Последствия**: `StageRun` закрывается по явному событию (босс убит), а не по эвристике значений. Корректная сегментация забегов питает агрегаты этапов (FR-007/FR-008) и интерпретацию темпа сундуков.

## ADR-013 — Хранилище: SQLite + EF Core

**Дата**: 2026-05-31
**Статус**: Accepted

**Контекст**: Нужна локальная персистентность истории забегов и агрегатов, переживающая перезапуск/перезагрузку (FR-011), с расширяемой схемой под новые механики без потери истории (FR-013/FR-021) и LINQ-агрегациями по этапам (FR-008).

## ADR-015 — UI-тесты живой игры: FlaUI + визуальная локализация, не Playwright

**Дата**: 2026-05-31 · **Статус**: Accepted

**Контекст**: требуется набор «нехрупких» детерминированных UI-тестов поверх реально запущенной игры — харнесс сам аудирует интерфейс, навигирует по разделам человекоподобными кликами, проверяет детекцию разделов и чтение значений (FR-022…FR-027).

**Решение**: отдельный QA-проект `TBHStats.UiTests` на **xUnit + FlaUI** (UIA + нативный ввод) + **визуальная локализация элементов** (OCR названий через переиспользование `TBHStats.Capture`) + **инъекция кликов SendInput** (случайная точка в границах элемента, случайная задержка, easing). - **Playwright** — браузерный инструмент; TBH — нативный десктоп (нет API, рендер на canvas/DirectX, UIA-дерево обычно недоступно). Применим только если игра окажется Electron с CDP (проверяется в TS-00) — не базовый путь.

- Чисто пиксельные клики — хрупкие; заменены на ассерты по распознанному состоянию + ожидания.

**Безопасность**: потребовался **carve-out конституции (v2.1.0 → v2.2.0)** — продукт observe-only, но QA-харнесс может инжектить ввод только в тест-режиме, с Safety-Guard (запрет необратимых действий: Runes/Cube/Stash/Trade).

**Последствия**: harness переиспользует продуктовый слой распознавания (двойная выгода — заодно валидирует Capture/детекцию). Эмпирический пункт: тип приложения TBH (нативное/Electron) определяется в TS-00, влияет лишь на наличие альтернативного CDP-пути.

## ADR-016 — Локальный файловый синк логирования: собственный FileLoggerProvider

**Дата**: 2026-05-31 · **Статус**: Accepted

**Контекст**: T047 требует персистентного синка логирования для диагностики приложения. Стек уже использует `Microsoft.Extensions.Logging`; нужен файловый провайдер с ротацией по дате, строго без сетевых зависимостей (FR-012: никаких исходящих сетевых соединений).

**Решение**: лёгкий собственный `ILoggerProvider` / `ILogger` (`FileLoggerProvider` + `FileLogger`, ~120 строк, `src/TBHStats.App/Services/Logging/`):
- Файл: `%LOCALAPPDATA%\TBHStats\logs\tbhstats-YYYY-MM-DD.log` (тот же базовый каталог, что и БД — `DatabaseInitializer.GetDbPath()`).
- Ротация по дате UTC: новый файл открывается при первой записи в новый день.
- Потокобезопасность: `lock (_writeLock)` на `StreamWriter`; `_writer.Flush()` после каждой записи.
- Минимальный уровень в файл: `Information` (Debug — только в `AddDebug()` для разработки; в файл не пишем, чтобы не раздувать).
- Регистрация в `App.BuildHost()` через `logging.AddProvider(new FileLoggerProvider(logDir, LogLevel.Information))`.
- Путь к лог-директории НЕ логируется на Info/Warning (PII — содержит имя пользователя).

**Альтернативы/почему отклонены**:
- **Serilog / NLog** — тянут сетевые синки в зависимости; избыточны для одного файлового синка; новая внешняя зависимость без реальной выгоды над собственными 120 строками.
- **ETW (EventSource)** — только для профилировщиков; нечитаемый «сырой» вывод для пользовательской диагностики.
- **`Microsoft.Extensions.Logging.AzureAppServices`** — облачный синк; нарушает FR-012.

**Последствия**: нет новых NuGet-зависимостей. Файловый синк полностью локален. Ротация по дате предотвращает рост одного файла. `FileLoggerProvider.Dispose()` корректно закрывает `StreamWriter` при остановке хоста.

## ADR-017 — Режим поставки: WindowsPackageType=None (default) + MSIX через MSBuild Desktop

**Дата**: 2026-05-31 · **Статус**: Accepted

**Контекст**: T048 требует настроить конфигурацию поставки MSIX (packaged) и опцию unpackaged. В проекте уже присутствуют `Package.appxmanifest` и `EnableMsixTooling=true`. Однако при попытке включить `<WindowsPackageType>MSIX</WindowsPackageType>` в `dotnet build` CLI возникает фатальная ошибка MSB4018 в задаче `WinAppSdkValidateAppxManifestItems` (пакет `Microsoft.Windows.SDK.BuildTools.MSIX` 1.7.x не находит `System.Security.Permissions` в MSBuild-хосте при запуске из dotnet CLI).

**Решение**: `<WindowsPackageType>` в csproj по умолчанию установлен в `None` (unpackaged). Это позволяет:
1. `dotnet build`/`dotnet run`/`dotnet test` работают без ограничений (unpackaged, `WindowsPackageType=None`).
2. Packaged MSIX-сборка активируется через MSBuild Desktop (Visual Studio 2022 ≥ 17.8 или `msbuild.exe` Desktop) с явным `/p:WindowsPackageType=MSIX`.
3. `Package.appxmanifest` исправлен: корректные `Identity.Name` / `DisplayName`, `MinVersion=10.0.19041.0` (синхронизировано с csproj `TargetPlatformMinVersion`), удалён лишний `systemai:Capability Name="systemAIModels"`, оставлен только `runFullTrust`. Сетевые capability отсутствуют (FR-012).
4. WinRT API (WGC, Windows.Media.Ocr) доступны в обоих режимах при TFM `net8.0-windows10.0.22621.0` через CsWinRT (подтверждено build + Capture.Tests 87 pass).

**Альтернативы / почему отклонены**:
- **`WindowsPackageType=MSIX` как default в csproj** — отклонено: ломает `dotnet build` в CLI из-за бага BuildTools.MSIX 1.7.x; разработчики и CI не смогут собирать без VS.
- **Отключить `WinAppSdkValidateAppxManifestItems` через `<DisableWinAppSdkValidateAppxManifestItems>true</DisableWinAppSdkValidateAppxManifestItems>`** — отклонено: скрывало бы будущие ошибки манифеста; правильнее разделить «сборку для разработки» и «MSIX-публикацию».
- **Одна конфигурация без MSIX** — отклонено: R6 требует packaged как предпочтительный режим финальной поставки; необходимо сохранить оба пути.

**Последствия**:
- Разработка, CI и portable-дистрибутив работают через `dotnet build/publish -p:WindowsPackageType=None`.
- Финальный MSIX-пакет собирается через VS «Package and Publish» или `MSBuild Desktop /p:WindowsPackageType=MSIX`.
- `Package.appxmanifest` поддерживается в актуальном состоянии: версия пакета должна обновляться вместе с `<Version>` в `Directory.Build.props` при релизах.
- Если BuildTools.MSIX обновится и устранит `System.Security.Permissions`-баг — `WindowsPackageType=MSIX` можно будет установить как default без последствий для `dotnet build`.

## ADR-018 — Мульти-позиционные ROI сундуков и детекция раскладки по `litCount == N`

**Дата**: 2026-06-01 · **Статус**: Superseded by ADR-022 (позиционная @N-схема идентификации типа заменена цветовой; инфраструктура ROI и resolver сохранены как legacy). Superseded by ADR-023 (зонная ROI заменяет per-ROI схему; per-ROI путь сохранён как fallback)

**Контекст**: Иконка каждого типа сундука в MainZone не имеет фиксированной позиции: присутствующие типы образуют горизонтально центрируемую группу, поэтому позиция иконки **одного и того же типа смещается** в зависимости от числа одновременно висящих типов `N` (1, 2 или 3) — например, у коричневого три разных местоположения для раскладок «только коричневый», «коричневый + ещё один», «все три». Прежняя модель калибровала ровно одну ROI на тип (`chest:brown`) и читала её фиксированно, что давало неверное чтение при двух и трёх типах. Дополнительный факт игры: **иконка типа пропадает при 0** полученных (все открыты / не выпадали).

**Решение**: Хранить **до трёх ROI на тип** через суффикс в `FieldKey`: `chest:<тип>@1`, `chest:<тип>@2`, `chest:<тип>@3`, где `N` — число одновременно присутствующих типов. Активная раскладка детектируется чисто на OCR, без анализа изображения иконок, на инварианте **«присутствует ⟺ `count ≥ 1`»** (следствие исчезновения иконки при 0):
- доменный `IChestLayoutResolver` (`TBHStats.Core/Parsing`) принимает показания всех `@N`-ROI и перебирает `N` от большего к меньшему;
- выбирается раскладка с **точным совпадением `litCount == N`** (число «горящих» `count≥1` ROI равно `N`); при неоднозначности — приоритет большему `N`;
- иначе fallback — `N` с максимальным `litCount > 0`; иначе `ChosenSlotCount = 0` (сундуков не видно).
- Разбор ключа — `ChestFieldKey.TryParse`; `@N`-ключи генерируются программно в `GameMechanicsConfig.CreateDefault()` (config-driven, ADR-009). Базовый `chest:<тип>` без `@N` сохранён как легаси «одна позиция» (обратная совместимость существующих калибровок). Эмпирическая донастройка — на живой игре (T049/T051).

**Альтернативы / почему отклонены**:
- **Отдельный ROI-детектор присутствия иконки (анализ изображения)** — отклонено: требует пиксельного анализа иконок вне текущего OCR-пайплайна; избыточен, т.к. «иконка пропадает при 0» уже даёт присутствие через `count ≥ 1`.
- **Поле-дискриминатор `LayoutSlotCount` в `RoiCalibration` + EF-миграция** — отклонено в пользу суффикса в `FieldKey`: не меняет схему БД (`FieldKey` уже строковый, `HasMaxLength(128)`), не требует миграции и переиспользует существующий плоский список калибровок.
- **Одна фиксированная позиция на тип (status quo)** — отклонено: даёт неверное чтение при 2 и 3 типах сундуков.

**Последствия**:
- Схема БД и миграции **не меняются**; существующие калибровки `chest:<тип>` продолжают работать.
- Логика выбора раскладки — чисто доменная (`TBHStats.Core/Parsing`), покрыта unit-тестами (раскладки 1/2/3 типа, неоднозначность, fallback, отсутствие). OCR остаётся в `FieldExtractor` (`TBHStats.Capture`).
- Уточняет ADR-011 (учёт по транзиентным точкам): резолвер определяет, какие точки какому типу принадлежат в текущей раскладке, после чего применяется логика «сумма положительных приростов».
- Калибровка: оператор размечает до трёх позиций на тип; экран калибровки предлагает `@N`-ключи и поясняет конвенцию.
- Документация: GAME-FACTS.md §5–§6, ARCHITECTURE.md §4/§9.

## ADR-019 — Мульти-панельный UI: чтение всех полей каждый кадр (снятие tab-gating) + апскейл OCR и порог уверенности

**Дата**: 2026-06-01 · **Статус**: Accepted

**Контекст**: На живой игре (2026-06-01) выявлено, что окно Task Bar Hero показывает **несколько разделов ОДНОВРЕМЕННО** (3 слота над MainZone + полноэкранный оверлей Rune — см. GAME-FACTS §2): центральный `Hero` (или Rune/Settings/Mail Box/Trade ship), левый `Status` (или Stash/Rune), правый `Cube/Portal/Rune`; `gold` — глобально вверху. Это **опровергает исходное предположение FR-002b** «одновременно открыт ровно один раздел», на котором строился gating полей по «активной вкладке» (`IFieldExtractor` читал Tab-поле только при совпадении `activeTab.TabId`). Из-за этого live-петля не читала gold/xp/heroLevel (детекция единственной активной вкладки давала `none`), хотя данные были видны. Дополнительно: Windows.Media.Ocr **не распознаёт слишком маленькие изображения** (мелкие ROI gold/xp/heroLevel высотой 18–27px возвращали пусто), а метрика уверенности — геометрическое покрытие — для коротких чисел даёт низкие значения (0.08–0.48 при верном чтении), несовместимые с прежним порогом 0.6.

**Решение**:
1. **Снять tab-gating в `FieldExtractor`**: читать ВСЕ калиброванные поля каждый кадр с их фиксированных позиций, независимо от `activeTab`. Валидация значения — парсером (`IValueParser`: число/время/этап обязаны корректно распарситься) и sanity-проверками (`IObservationValidator`: монотонность золота и т.п.). Закрытый раздел/чужой слот не даёт валидного значения → поле сохраняет прежнее. `activeTab`/`ITabDetector` для чтения полей больше не используются (поле `RawObservation.ActiveTab` остаётся информационным).
2. **Апскейл маленьких кропов перед OCR** (`OcrReader`): если меньшая сторона вырезанной области < 64px — увеличить целочисленным множителем (cap по `OcrEngine.MaxImageDimension`) перед `RecognizeAsync`. Уверенность считать по площади реального OCR-входа.
3. **Понизить порог уверенности** `StatsOrchestrator.ConfidenceThreshold` 0.6 → 0.02 (геометрическое покрытие — слабый прокси; основная валидация — парсер+sanity).

**Альтернативы / почему отклонены**:
- **Слот-зависимая детекция** (OCR заголовка каждого слота → принимать поле только если в слоте нужный раздел) — более устойчиво к контаминации, но сложнее; отложено как возможное будущее уточнение. Для v1 достаточно read-all + парсер/sanity (пользователь держит нужные панели открытыми).
- **Оставить tab-gating, чинить детекцию activeTab** — отклонено: модель единственной активной вкладки не соответствует мульти-панельному UI.
- **Поднимать качество OCR без апскейла** — отклонено: ограничение минимального размера — свойство Windows.Media.Ocr (подтверждено Microsoft Q&A); апскейл — стандартное решение.

**Последствия**:
- `gold`/`xp`/`xpToLevel`/`heroLevel`/`heroDamage`/`heroClass`/`xpPair` читаются на живой игре (мелкие зоны — благодаря апскейлу) и принимаются (порог 0.02). Калибровочный экран получил живой OCR-предпросмотр с уверенностью для точной разметки.
- **Расхождение со spec FR-002b**: это derived-docs фиксация; обновление самого требования (single-tab → multi-panel read-all) — через `/speckit`-amend и Amendment Procedure конституции. До синхронизации первоисточник по поведению — данный ADR + GAME-FACTS §2.
- Риск контаминации (чужой раздел в слоте) снижается парсером/sanity; при необходимости вводится слот-зависимая детекция.
- Остаются P2-уточнения: `stageId` (узкая зона на текущий этап вместо всей карты Portal), `stageTime`/завершение этапа (по `stageProgress`, т.к. инфо-лента редко показывает время), `stageProgress` (визуальный прогрессбар — детекция изображения, T035, не OCR), **подсчёт сундуков** (точки графические, не текст → визуальный детектор точек, не OCR; инфраструктура `chest@N`+`ChestLayoutResolver` сохраняется).
- UI-уточнения (2026-06-01): поле «Этап» виджета = `nextLocation − 1` (`StageRef.Previous`); режим «поверх всех окон» (`AlwaysOnTop`) отключён по требованию (виджет не закрепляется поверх).

## ADR-020 — Золото — расходуемый баланс: монотонность золота не гейтит надёжность сэмпла

**Дата**: 2026-06-01 · **Статус**: Accepted (уточняет ADR-019)

**Контекст**: На живой игре (2026-06-01) выявлено зависание виджета после открытия вкладки **Rune**: данные переставали обновляться и не восстанавливались ~2 минуты после её закрытия. По логам — во время перекрытия Status вкладкой Rune поля Status недоступны (ожидаемо stale), но и ПОСЛЕ закрытия, когда `gold`/`xp`/`heroLevel` снова читались, сэмплы оставались ненадёжными. Причина — проверка монотонности золота в `ObservationValidator` (`isReliable = hasSignificantField && !goldViolation`, где `goldViolation` = убывание `gold` относительно prevReliable): во вкладке Rune игрок **тратит золото** на прокачку рун → общий баланс **легитимно убывает**, и реальное (сниженное) gold браковало ВЕСЬ сэмпл — включая валидные `xp`/`heroLevel` — пока баланс не дорастал обратно. Исходное допущение «золото — монотонный кумулятив» (`research.md` R4) оказалось неверным: золото — **расходуемый баланс** (руны/апгрейды/магазин).

**Решение**:
1. Убрать `goldViolation` из критерия надёжности `ObservationValidator`: `isReliable = hasSignificantField` (`gold`/`xp`/`heroLevel`). Убывание золота — легитимная трата, не нарушение sanity, не делает сэмпл ненадёжным.
2. Фактический (в т.ч. сниженный) баланс записывается в `MetricSample.Gold` — корректное отображение.
3. Темп «золото/час» (`MetricsCalculator`) как и прежде считает только **положительные** дельты (заработок); трата (убыль) даёт вклад 0 — поэтому трата не искажает темп.
4. Защита темпов от выбросов (misread / разовая награда / продажа инвентаря) обеспечивается отдельным детектом выброса ставки (`RateOutlierDetector`, см. ARCHITECTURE §9), а НЕ проверкой монотонности золота. Это уточняет sanity-ссылку из ADR-019 (решение #1: «монотонность золота» в `IObservationValidator` снята).

**Альтернативы / почему отклонены**:
- **Оставить монотонность, отбрасывая только поле gold (не весь сэмпл)** — частично решает заморозку, но сохраняет риск ложного всплеска золото/ч при восстановлении после misread и не отражает доменный факт «золото расходуемо». Отклонено в пользу прямого признания расходуемого баланса.
- **Детектить трату по контексту вкладки Rune** — хрупко (класс/вкладка читаются не каждый кадр); монотонность всё равно не нужна, т.к. темп считает только заработок.

**Последствия**:
- Виджет не зависает после траты золота — `xp`/уровень/темпы обновляются, золото показывает реальный сниженный баланс.
- **Расхождение со spec исправлено в первоисточниках напрямую**: `research.md` R4 (правило монотонности → «золото расходуемо»), `data-model.md` (`Gold` = баланс, `IsReliable`), `spec.md` (краевой случай «Трата золота»). Derived-docs — GAME-FACTS §10, ARCHITECTURE §9.
- Остаточный риск: единичный заниженный misread `gold` с последующим восстановлением может дать разовый ложный вклад в золото/ч (сглаживается окном 90 с + EMA); при проявлении — распространить `RateOutlierDetector` на золото (это также подавит всплеск от продажи инвентаря, edge-case `spec.md`).

## ADR-021 — Визуальный детектор точек сундуков заменяет OCR-счёт; инфраструктура @N сохраняется

**Дата**: 2026-06-01 · **Статус**: Accepted

**Контекст**: Точки под иконками сундуков в MainZone — **графические** (не текстовые): `Windows.Media.Ocr` их не читает. До T062 `FieldExtractor` пытался читать chest-ROI через `IOcrReader.ReadAsync` + `TryParseAbbreviatedNumber`, что возвращало пустой результат (`Recognized=false`). Счёт сундуков фактически не работал. Инфраструктура мульти-позиционных ROI `chest:<тип>@N` + `IChestLayoutResolver` (ADR-018) корректна для геометрии раскладки и должна быть сохранена; нужно только сменить **источник счёта** с OCR на анализ пикселей.

**Решение**:
1. Новый компонент `IChestDotCounter` / `ChestDotCounter` в `TBHStats.Capture/Chests/` — визуальный детектор, не использующий OCR:
   - Кроп ROI → Bgra8 пиксельный буфер (кэш на кадр, аналог `OcrReader`).
   - Для каждой вертикальной колонки ROI: доля тёмных пикселей (`luminance=0.299R+0.587G+0.114B < DarkThreshold=90`). Колонка «тёмная» при `darkFraction ≥ MinDarkColumnFraction=0.3`.
   - Непрерывный run «тёмных» колонок шириной ≥ `MinRunWidthPx=3` = одна заполненная точка.
   - Детекция паттерна: `hasBrightPixel=true` (lum > BrightThreshold=210 в любом пикселе) ИЛИ `filledDots > 0` → `Detected=true`.
   - Пороги выверены по `screenshots/chests.jpg` (545×241): red=1, blue=1, brown=2 (ground truth, verified T062).
     Brown точки тёмны только 4 строки из 13 строк ROI (darkFraction≈0.31 ≥ 0.3); red/blue — 6 строк (≈0.46 ≥ 0.3).
   - Результат `ChestDotCountResult(Count, Detected)`.
2. `FieldExtractor` в ветке `ChestFieldKey.TryParse(...)` теперь вызывает `IChestDotCounter.CountFilledDotsAsync` вместо `IOcrReader.ReadAsync`. Если `Detected=false` — пропускает поле (как прежде `!res.Recognized`). Поток `@N → ChestLayoutResolver.Resolve` не меняется.
3. `IChestDotCounter` зарегистрирован в DI (`Composition.AddTbhStatsServices`) как singleton.

**Альтернативы / почему отклонены**:
- **Пиксельный детектор присутствия иконки** для определения раскладки — отклонено в ADR-018; инвариант `litCount==N` на OCR достаточен. Текущее решение не затрагивает resolver.
- **Tesseract с whitelist "0123456789"** для точек — отклонено: точки вообще не текст; никакой OCR-движок их не прочитает.
- **Сохранение OCR в chest-ветке** — отклонено: OCR неприменим к графическим пикселям; реальные точки имеют luminance 8–86 и не содержат символов.
- **Добавить OCR-fallback для точек** — отклонено: fallback бессмысленен, если основной механизм работает корректно (4 pass на фикстуре).

**Последствия**:
- Chest-ROI больше **не вызывают OCR** в `FieldExtractor` — исключена бесполезная WinRT async-операция на каждый кадр per тип сундука.
- Пороги детектора (`DarkThreshold=90`, `BrightThreshold=210`, `MinDarkColumnFraction=0.3`, `MinRunWidthPx=3`) — именованные константы с XML-doc в `ChestDotCounter.cs`.
- Эмпирическое ограничение: пороги настроены по `chests.jpg`; точность на живой игре при других масштабах окна, DPI или теме ОС требует уточнения в T049/T051.
- Правильный x-диапазон ROI критичен для brown-типа: ROI должен начинаться после левой рамки панели сундука (иначе рамка 6px создаёт ложный run). Red/blue панели имеют средние пиксели рядом с точками (lum=143–157 > DarkThreshold=90) — ложных run-ов нет.
- Документация: ARCHITECTURE.md §3 (OCR), §4 (ROI/chest), GAME-FACTS.md §5–§6.

## ADR-022 — Идентификация типа сундука по цвету фона плашки заменяет позиционную @N-схему

**Дата**: 2026-06-01 · **Статус**: Accepted (per-ROI путь сохранён как fallback в ADR-023) · **Supersedes**: ADR-018 (позиционная @N-идентификация)

**Контекст**: ADR-018 ввёл схему `chest:<тип>@N`-ROI: тип сундука определялся по ключу ROI, а `IChestLayoutResolver` выбирал активную раскладку `N` по числу «горящих» ROI. На живой игре выявлен критический баг: при раскладке «2 типа» (brown+blue или brown+red) второй слот — общий для blue и red; позиция иконки не различает эти типы, различает только **цвет фона плашки**. Следствие: `red@2`-ROI над синей плашкой → FieldExtractor присваивал `typeId=red`, давая фантомный `red=3` при отсутствии красного и `blue=5` вместо 2.

Эмпирически (фикстура `screenshots/chests.jpg`, 545×241) подтверждено: каждый тип сундука имеет **стабильный цвет фона плашки**: red → orange (236,133,41), R≫B; blue → lightblue (190,220,238), B>R; brown → white (255,255,255), R≈G≈B. Цвет стабилен и однозначно идентифицирует тип. Расстояния между якорями: orange↔white ≈190, lightblue↔white ≈75, orange↔lightblue ≈210.

**Решение**:
1. Новый контракт `IChestPanelAnalyzer` / `ChestPanelReading(ChestTypeId?, DotCount, PanelMatch)` в `TBHStats.Capture/Chests/`. `ChestDotCounter` реализует оба интерфейса (`IChestDotCounter` + `IChestPanelAnalyzer`).
2. Алгоритм `AnalyzeChestPanelAsync`:
   - ROI теперь должен накрывать **всю плашку целиком** (не только полосу точек).
   - Сбор ярких пикселей (luminance ≥ `BrightPanelThreshold=110`): фон плашки + белые ячейки; тёмный спрайт иконки исключается.
   - Медиана R/G/B по ярким пикселям = `panelColor` (устойчива к спрайту).
   - Reject, если доля ярких пикселей < `MinBrightCoverage=0.25` (тёмная сцена вне плашек).
   - Евклидово расстояние до якорей `ChestType.PanelColor` (из `GameMechanicsConfig`); reject, если расстояние > `ColorMatchTolerance=70`.
   - Счёт точек: нижние `DotStripFraction=0.38` высоты ROI (ряд точек) → run-алгоритм по яркости; `MinRunWidthPx` увеличен с 3 до 4 (исключает ложные run-ы краёв рамки ~3px).
   - `PanelMatch = (1 - dist/(Tolerance*2)) * brightCoverage` — мера уверенности для мёрджа.
3. `FieldExtractor`: тип из цвета (`IChestPanelAnalyzer`), **не из ключа ROI**. Мёрдж: несколько ROI на один тип → выбирается с наибольшим `PanelMatch`. `IChestLayoutResolver` больше не вызывается в пайплайне (удалена зависимость из ctor). Сам `ChestLayoutResolver`/`IChestLayoutResolver` в Core **не удалён** — помечен как legacy.
4. DI в `Composition.cs`: `ChestDotCounter` регистрируется как единственный экземпляр, отдающий обоих интерфейсов.

**Якорные цвета** (`GameMechanicsConfig.CreateDefault()`, засижены в Task A):
- brown: (255,255,255) — белый/серый фон
- blue: (190,220,238) — голубой
- red: (236,133,41) — оранжевый

**Альтернативы / почему отклонены**:
- **Зафиксировать ROI жёстче, чтобы blue@2 и red@2 не пересекались** — неприменимо: при раскладке «2 типа» второй слот физически один и тот же (центрирование группы); позиция не различает тип.
- **Пиксельный детектор иконки (template matching)** — отклонено: сложнее; цветовая дистанция проще, надёжнее (один порог) и быстрее.
- **Сохранить `IChestLayoutResolver` в пайплайне** — отклонено: он не нужен после перехода на цветовую идентификацию; его логика (выбор `N` по litCount) теперь избыточна.

**Последствия**:
- Фантомные показания типа (`red=3` / `blue=5` при неверной раскладке) устранены: тип берётся из цвета, независимо от ключа ROI.
- **Важное изменение требований к калибровке**: chest-ROI обязан накрывать **всю цветную плашку** (а не только полосу точек внизу) — иначе `brightCoverage` не наберёт порог и классификация упадёт в reject.
- `IChestDotCounter.CountFilledDotsAsync` (прежний ROI «только полоса точек») сохранён для обратной совместимости; в новом пайплайне не используется.
- Пороги: `BrightPanelThreshold=110`, `MinBrightCoverage=0.25`, `ColorMatchTolerance=70`, `DotStripFraction=0.38`, `MinRunWidthPx=4`.
- Тесты: `ChestPanelAnalyzerFixturesTests` (6 тестов): red=1/blue=1/brown=2 ground truth; регресс-тест (`red@2`-ключ над синей → blue); негатив (тёмная сцена → null).
- Эмпирическое ограничение: white-фон плашки brown (255,255,255) — ближайший к медиане пустых ячеек. При маленьком ROI без плашки, где случайно много белых пикселей, возможен ложный brown. Митигирует `MinBrightCoverage`: тёмная сцена не набирает 25%.
- Документация: ARCHITECTURE.md §4 (ROI/chest), GAME-FACTS.md §6.

## ADR-023 — Зонная локализация плашек по цвету + масштабонезависимый счёт точек по строкам

**Дата**: 2026-06-01 · **Статус**: Accepted · **Supersedes**: ADR-022 (как приоритетный метод; per-ROI путь ADR-022 сохранён как fallback) и ADR-018 (позиционная @N-схема)

**Контекст**: ADR-022 исправил фантомные значения типов, перейдя на цветовую идентификацию. Однако при фиксированных per-ROI-на-тип значения по-прежнему давали сбои: (1) при переуплотнении группы (1/2/3 типа) ручные ROI обрезали ряды точек; (2) `DotStripFraction=0.38` (фиксированная нижняя доля ROI) совместно с произвольным расположением ROI пользователем приводила к недосчёту: -1 от ground truth на нескольких фикстурах. Подтверждено на фикстуре `main.jpg` (549×232): blue=3, brown=3, но с per-ROI схемой стабильно получались 2 вместо 3. Причина: JPEG-сжатие сужает run-ы точек до 3–4px, а фиксированный MinRunWidthPx=4 их отсекал; плюс нижняя рамка плашки «засвечивала» зазоры.

**Решение**: Новый компонент `IChestZoneAnalyzer`/`ChestZoneAnalyzer` в `TBHStats.Capture/Chests/`:
1. **Одна зонная ROI** `chestZone` (FieldKey=`"chestZone"`, Source=MainZone) охватывает всю горизонтальную группу плашек. Пользователь калибрует одну широкую зону вместо N×3 per-ROI.
2. **Горизонтальная сегментация по цвету**: для каждой вертикальной колонки зоны — медиана R/G/B ярких пикселей (lum ≥ `BrightPanelThreshold=120`); евклидово расстояние до якорей `ChestType.PanelColor` ≤ `ColorMatchTolerance=60`. Сегмент = смежные колонки одного типа шириной ≥ `MinPanelWidthFraction=0.06` × ширина зоны.
3. **Масштабонезависимый счёт точек**: нижний пояс (`DotZoneFraction=0.32` × высота зоны). Строки фильтруются: включаются строки с `darkRowFraction ∈ [0.05, 0.45)` — исключается светлый фон (< 0.05) и тёмная рамка/сцена (≥ 0.45). По отфильтрованным строкам строится агрегированный профиль тёмных пикселей; run-алгоритм: `minRunPx = segW/5 × MinRunCellWidthFraction=0.15` (масштабонезависимо), `maxRunPx = 0.35 × segW` (антиспрайт).
4. **`FieldExtractor`**: при наличии `chestZone`-ROI → вызывает `IChestZoneAnalyzer.AnalyzeZoneAsync` → результат в `Chests`; per-ROI `IChestPanelAnalyzer`-путь не выполняется. При отсутствии `chestZone`-ROI → fallback на per-ROI `IChestPanelAnalyzer` (ADR-022).
5. **`GameMechanicsConfig.CreateDefault()`**: добавлен binding `"chestZone"` → MainZone; `@N`-биндинги сохранены как legacy.

**Верификация**: два теста `ChestZoneAnalyzerFixturesTests` на реальных фикстурах:
- `chests.jpg` (545×241): зона x≈0.358..0.899, y≈0.228..0.539 → red=1, blue=1, brown=2 ✓
- `main.jpg` (549×232): зона x≈0.446..0.810, y≈0.207..0.509 → blue=3, brown=3, red отсутствует ✓

**Альтернативы / почему отклонены**:
- **Продолжать per-ROI схему с дополнительными порогами** — отклонено: корень проблемы в том, что при переуплотнении группы единственная надёжная схема — захватывать всю зону целиком и локализовывать плашки автоматически.
- **Template matching по спрайту иконки** — отклонено: цветовая медиана проще, быстрее и надёжнее при JPEG-артефактах.
- **Фиксированный MinRunWidthPx** — отклонено: при масштабах main.jpg (~105px сегмент) 4px-порог отсекал реальные точки; относительный порог `0.15 × cellWidth` решает задачу для диапазона масштабов.

**Последствия**:
- Пользователь калибрует **одну зону** вместо per-ROI на каждый тип × раскладку.
- Счёт точек верный на двух фикстурах разного масштаба: chests.jpg (545×241) и main.jpg (549×232).
- `IChestZoneAnalyzer` зарегистрирован как singleton в DI (`Composition.cs`); `FieldExtractor` принимает оба анализатора.
- ADR-018/ADR-022 per-ROI инфраструктура полностью сохранена; `IChestDotCounter`/`IChestPanelAnalyzer` и `@N`-ключи работают как fallback.
- Документация: ARCHITECTURE.md §4 (зонная ROI, алгоритм), GAME-FACTS.md §6 (многорядность точек, зонный детектор).

## ADR-024 — Визуальная детекция прогресса этапа по цвету заливки (фиолетовый/синий)

**Дата**: 2026-06-02 · **Статус**: Accepted

**Контекст**: В правом-нижнем углу MainZone расположен горизонтальный прогрессбар текущего этапа. Заливка движется справа налево: тёмный трек (начало) → фиолетовый «след» (прохождение) → весь бар фиолетовый (конец пути, ≈95%) → весь бар синий (бой с боссом, 100%). OCR неприменим — бар графический, без текста. Метаданные: ROI FieldKey `"stageProgress"` (Source=MainZone); `"bossPresent"` логически вторичен (извлекается из того же кадра).

**Решение**: Новый компонент `IStageProgressReader`/`StageProgressReader` в `TBHStats.Capture/Progress/`. Алгоритм поколоночный по вертикальным колонкам ROI; итоговая версия (после калибровки на живой игре, см. «Эволюция» ниже):
1. **Высото-устойчивая классификация колонок.** Для каждой колонки считается АБСОЛЮТНОЕ число фиолетовых / синих / тёмных пикселей; колонка классифицируется по преобладающему цвету при ≥ `MinColoredPixelsPerColumn=3`. Абсолютный порог (а не доля высоты) устойчив к ROI, нарисованному «на глаз» выше тонкой полоски (~6px). Тёмные пиксели (luminance < `DarkLumThreshold=40`) НЕ классифицируются по цвету (иначе тёмно-фиолетовый тон пустого трека ложно «заполнял» бы бар).
2. **Относительная цветовая модель** (инвариант к насыщенности; пиксельные константы рендера, NOT из `GameMechanicsConfig`). Якоря заливки сильно разнятся по насыщенности между JPEG-фикстурами (фиолетовый ≈165,77,213) и живым WGC-кадром (≈130,98,150 — заметно менее синий), поэтому абсолютные пороги (`B>150`) отсекали тусклый живой фиолетовый. Различение по структуре каналов:
   - Фиолетовый (магента-violet): (R−G) ≥ `PurpleChannelMargin=12` И (B−G) ≥ 12 (R и B выше G; зелёный минимален).
   - Синий (бирюзовый, бой с боссом): (B−G) ≥ `BlueBlueOverGreenMargin=5` И (G−R) ≥ `BlueGreenOverRedMargin=25` (красный минимален).
   - Разделитель: у фиолетового R>G, у синего R<G — взаимоисключающе.
3. **Прогресс по доле трека + ремап мёртвых зон.** `blueColumns/roiW ≥ 0.20` → BossPresent=true, Progress=0.95 (этап НЕ пройден, пока босс жив; 100% — только в момент завершения, когда бар сброшен). Иначе путь: `purpleTrackFraction = purpleColumns/(purpleColumns+darkColumns)` (нормировка по треку исключает стрелку-маркер и светлые края). Линейный ремап рабочего диапазона `[RawTrackEmpty=0.12 .. RawTrackFull=0.84] → [0..1]` × 0.95: стрелка-маркер даёт ненулевую заливку у пустого бара (~13%), а десатурированный край у стрелки не дотягивает у полного (~0.84) — ремап даёт чистые 0% (пусто) и 95% (полный). Нечитаемый ROI → null/null.
4. `StageProgressReading` — `readonly record struct(double? Progress, bool? BossPresent)`. Диагностический метод `DiagnoseAsync` → `StageProgressDiagnostic` (счётчики колонок + образец цвета) питает предпросмотр экрана калибровки (визуальная проверка ROI на живом кадре).
5. `FieldExtractor`: при FieldKey=`"stageProgress"` и флаге `StageProgressDetectionEnabled=true` → вызов reader; результат в `RawObservation.StageProgress`/`BossPresent`. FieldKey `"bossPresent"` пропускается отдельно — данные из одного ROI. Флаг позволяет быстро отключить функцию без удаления кода.
6. Кэш буфера кадра: паттерн `GetOrFillFrameCache(SoftwareBitmap)` из `ChestZoneAnalyzer` — конверсия в Bgra8 Premultiplied, ключ ReferenceEquals, lock.

**Верификация**: пороги выверены на 4 фикстурах + калибровке на живой игре:
- `progress_begin.jpg` (554×243): бар пустой → progress=0.0, BossPresent=false.
- `progress_half.jpg` (548×247): фиолетовый x[504..540] → progress≈0.52, BossPresent=false.
- `progress_full.jpg` (559×236): фиолетовый x[482..550] → progress=0.95, BossPresent=false.
- `progress_stagebossfight.jpg` (552×247): синий x[475..543] → progress=0.95, BossPresent=true.
- Живая игра (после калибровки): пусто→1%, середина→49%, полный→93–95%, босс→95%·да, после убийства босса→сброс к ~0%.

**Эволюция (калибровка на живой игре 2026-06-02)**: первая версия использовала абсолютные цветовые пороги (`B>150`) и `progress = purpleFraction/roiW × 0.95`. На живом кадре это давало «всегда 0%» (порог высоты колонки 0.40 при ROI выше полоски), затем недосчёт (живой фиолетовый менее синий) и компрессию (стрелка-маркер + десатурированный край). Итеративно по диагностике приведено к: высото-устойчивый абсолютный счёт → относительная цветовая модель → нормировка по треку → ремап мёртвых зон. Константы `RawTrackEmpty`/`RawTrackFull` откалиброваны по живой диагностике и задокументированы как эмпирические (тюнятся при изменении ROI/рендера).

**Альтернативы / почему отклонены**:
- **OCR прогрессбара** — неприменим: бар не содержит текста, только цветную заливку.
- **Детекция по позиции стрелки (template matching)** — отклонено: цветовой анализ проще и надёжнее при JPEG-артефактах; стрелка мала и чувствительна к масштабу.
- **Абсолютные цветовые пороги** — отклонены после живой калибровки: насыщенность заливки сильно разнится между JPEG-фикстурами и WGC-кадром; относительная структура каналов инвариантна.
- **Конфиг-driven цветовые якоря в `GameMechanicsConfig`** — отклонено: прогрессбар — единый элемент UI с двумя фиксированными состояниями (фиолетовый/синий), не «игровая механика»-справочник (в отличие от ChestType с якорями). Пороги хардкожены как XML-doc-комментированные константы, как `DarkThreshold`/`BrightPanelThreshold` в `ChestZoneAnalyzer`.

**Последствия**:
- `RawObservation.StageProgress` и `BossPresent` теперь реально заполняются `FieldExtractor` при наличии `stageProgress`-ROI в калибровке.
- `StageCompletionDetector` получает реальные данные: переход `BossPresent true → false` корректно детектирует завершение этапа.
- Семантика null сохранена: null = «ROI не откалиброван / кадр нечитаемый»; детектор отличает null от false.
- DI (`Composition.cs`): `IStageProgressReader` → `StageProgressReader` (singleton) — регистрация выполняется отдельно в App-слое.
- `FieldExtractor` принимает 5-й параметр `IStageProgressReader` (breaking change для конструктора).
- Экран калибровки (`CalibrationViewModel`): для ROI `"stageProgress"` предпросмотр вызывает `DiagnoseAsync` (визуальный детектор, не OCR) и показывает «Прогресс: N% · босс: да/нет» + диагностику (счётчики колонок, образец RGB) для калибровки ROI на живом кадре. `CalibrationViewModel` принимает `IStageProgressReader` (6-й параметр).
- Документация: ARCHITECTURE.md §3 (визуальная детекция прогресса).

## ADR-025 — Сегментно-управляемая запись забегов + гейтинг распознавания этапа + ретенция 10 забегов

**Дата**: 2026-06-02 · **Статус**: Accepted

**Контекст**: До T064 запись `StageRun` управлялась `RunRecorder`, который использовал `IStageCompletionDetector` (момент гибели босса) как триггер и сам накапливал gold/xp/chest между стартом и завершением забега. Параллельно `StatsOrchestrator` уже вычислял «время предыдущего этапа» (`_lastCompletedStageSeconds`) **по другому механизму** — границе сегмента по падению визуального прогресса (`StageProgress`) после боя с боссом (ADR-024). Два независимых механизма сегментации давали расхождения: время этапа считалось по прогрессу, а забег закрывался по событию детектора — моменты не совпадали, gold/xp забега не были согласованы со скобочным «за этап». Дополнительно: забеги могли записываться с нераспознанным этапом (когда `nextLocation` не виден — первый проход / босс акта), портя статистику; число забегов на этап росло неограниченно, размывая recency-aware рекомендацию (ADR-013/§7).

**Решение**:
1. **Единый сегментный триггер.** Запись `StageRun` перенесена из `RunRecorder` в `StatsOrchestrator` и привязана к той же границе сегмента, что и «время предыдущего этапа»: падение `StageProgress` на `≥ StageProgressDropThreshold (0.10)` при `_bossSeenInSegment && _segmentStartedFromReset` (сегмент начат от наблюдаемого сброса, босс был замечен). Gold/xp/сундуки за этап накапливаются **по сегменту** в `StatsOrchestrator` (`AccumulateSegment`/`StartNewSegment`): золото = `Max(0, _lastKnownGold − _segmentStartGold)`, опыт = сумма положительных внутрисегментных дельт с компенсацией level-up, сундуки = сумма положительных дельт мгновенных точек (ADR-011). `IStageCompletionDetector` запись больше **не управляет** (класс остаётся в DI/контрактах, но `RunRecorder` его не вызывает).
2. **`RunRecorder` → тонкий сервис персиста.** `PersistSegmentRunAsync(stageId, durationSeconds, goldGained, xpGained, chests, heroLevel, heroDamage, heroClassText, completedAtUtc, ct)` принимает готовые сводные данные, собирает `StageRun` + `HeroSnapshot`, пишет через `IRunRepository.AddRunAsync` и пересчитывает агрегат. Состояния накопления нет; `Reset()` — no-op.
3. **Гейтинг распознавания этапа.** Забег записывается только если этап распознан из свежего `nextLocation` в течение сегмента (`_segmentStageId.HasValue` — `sample.StageId` зарезолвился через `cfg.ResolveStageId`). Иначе забег НЕ записывается (Debug-лог), а виджет показывает «—» в строке «Этап» (`_currentStageRecognized == false`). Антифликер-стабилизатор `nextLocation` сохранён; гейт работает на уровне сегмента.
4. **Ретенция ≤10 забегов на этап.** После записи нового забега и **до** пересчёта агрегата вызывается `IRunRepository.PruneOldRunsAsync(stageId, keepLast=10, ct)` — физически удаляет все `StageRun` этапа сверх 10 самых свежих (`CompletedAtUtc DESC, Id DESC`). Агрегат считается по ≤10 свежим забегам. **Схема БД не менялась** (только bulk-delete, новой миграции нет).

**Альтернативы / почему отклонены**:
- **Оставить два механизма (детектор для записи + прогресс для времени)** — отклонено: рассинхрон моментов завершения, несогласованные gold/xp забега и «за этап», дубль-логика сегментации (см. ADR-012/ADR-024 — теперь источник сегментации один).
- **Записывать забег и при нераспознанном этапе (привязка к `_lastKnownStage`)** — отклонено: риск приписать забег чужому/устаревшему этапу при невидимом `nextLocation` (первый проход, босс акта) → порча статистики; гейт по свежему распознаванию надёжнее.
- **Хранить всю историю забегов без прунинга** — отклонено: рост таблицы + размытие recency-aware рекомендации старыми забегами при низкой силе отряда. Прунинг по `keepLast` дешевле и стабильнее, чем по времени, и согласован со «свежим окном» оптимизации (§7).
- **Новая миграция/таблица под ретенцию** — не потребовалась: bulk-delete по существующей схеме достаточен.

**Последствия**:
- Уточняет **ADR-012** (сигнал завершения этапа): механизм сегментации забегов — падение визуального прогресса после босса (ADR-024) в `StatsOrchestrator`, а не событие `IStageCompletionDetector`; детектор сохранён, но из пути записи исключён.
- Уточняет **ADR-013** (хранилище): вводит ретенцию ≤10 `StageRun` на этап (`PruneOldRunsAsync`) без изменения схемы; агрегат считается по свежему срезу.
- `LiveStatsSnapshot` получил поля `LastCompletedStageGold`, `LastCompletedStageXp` (показ золота/опыта за предыдущий этап в скобках — §7).
- UI: из виджета убрана кнопка «Графики» (Alt+G), в таблице сравнения номер этапа и сложность разделены (`StageNumberLabel`/`DifficultyLabel`), колонка сложности и колонка «Сила» скрыты (данные сложности/силы сохраняются в БД, но не отображаются) — §7.
- Документация: ARCHITECTURE.md §6 (ретенция), §7 (виджет/таблица сравнения), §9 (сегментная запись + гейтинг), §11 (`RunRecorder`/`IStageCompletionDetector`).

## ADR-026 — Игровой скин виджета (фиксированная палитра) + управление позицией окна игры через SetWindowPos

**Дата**: 2026-06-02 · **Статус**: Accepted

**Контекст**:
1. **Игровой скин.** Виджет использовал системные WinUI 3 цвета (Light/Dark тема), что не соответствовало визуальному стилю самой игры Task Bar Hero (тёмный фон, бордовые плашки, золотой/кремовый текст — скриншот `screenshots/status_1.jpg`). Планируемое решение T053 (адаптивная тема, ADR-002) предполагало `ThemeResource`-кисти для адаптации к системной теме. Однако визуальное соответствие игре важнее адаптивности: продукт работает рядом с игрой и должен ассоциироваться с ней.
2. **Управление позицией окна игры.** Для освобождения экрана без потери WGC-захвата (статистика должна собираться) требуется возможность убрать окно игры из видимой зоны. Стандартные Win32 `SW_MINIMIZE`/`SW_HIDE` убирают окно из DWM-композиции → WGC-захват прерывается → состояние захвата переходит в `Waiting` → статистика не собирается. При этом перемещение окна на off-screen координаты через `SetWindowPos` оставляет его в DWM-композиции, видимым для WGC.

**Решение**:
1. **Фиксированная игровая палитра в `GameWidgetStyles.xaml`.** Ресурсный словарь `src/TBHStats.App/Themes/GameWidgetStyles.xaml` определяет все игровые кисти (`GameBackgroundBrush`, `GameAccentBrush`, `GameHeaderForegroundBrush`, `GamePanelBackgroundBrush` и др.), стили TextBlock (`GameHeaderTextStyle`, `GameLabelTextStyle`, `GameValueTextStyle`, `GameCaptionTextStyle`), стили Border (`GamePanelBorderStyle`, `GameHeaderBorderStyle`), `GameButtonStyle`, `GameCheckBoxStyle`, шрифт `GamePixelFont` (Pixelify Sans, SIL OFL). `WidgetWindow.xaml` использует ТОЛЬКО эти ресурсы — никакого `ThemeResource ApplicationPageBackgroundThemeBrush` в RootGrid и никакого хардкода `Color=`. Статус-плашки («Игра не найдена» / «Ожидание») сохраняют семантику через валидные WinUI 3 `SystemFillColorCritical*/Caution*` кисти, шрифт унифицирован через `GamePixelFont`. Решение отступает от адаптивной темы T053 в пользу визуальной идентичности продукту.
2. **`IGameWindowController` / `GameWindowController` (`SetWindowPos` off-screen).** Окно перемещается на координаты (−32000, −32000) через `SetWindowPos` с флагами `SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE`. Исходная позиция сохраняется в `_savedRect`; `Restore` возвращает на неё. `IsHidden` — потокобезопасный флаг состояния (lock). Продукт остаётся **observe-only по вводу**: `SetWindowPos` перемещает окно, но не инжектирует клавиши, мышь или сообщения в игровой процесс. `IGameWindowController` зарегистрирован в DI как singleton (`Composition.cs`). В `WidgetWindow` при закрытии — автоматический `Restore`.

**Альтернативы / почему отклонены**:
- **Адаптивная тема (`ThemeResource`-кисти, T053/ADR-002)** — отклонена для виджета: системные цвета Light/Dark нарушают визуальную идентичность с игрой; пользователь запускает виджет рядом с игрой → ожидает стилистического соответствия. Адаптивная тема нецелесообразна для «игрового помощника». Задел на MAUI (ADR-010) сохранён: `GameWidgetStyles.xaml` не содержит WinRT-зависимостей в ресурсах (только `SolidColorBrush`/`Style`), портируется тривиально.
- **`SW_MINIMIZE` для сокрытия окна игры** — отклонено: убирает окно из DWM-композиции → WGC-сессия прерывается → `CaptureState.Waiting` → статистика останавливается. Именно это и нужно избежать.
- **`SW_HIDE` (невидимое окно)** — отклонено: аналогично `SW_MINIMIZE` убирает из DWM → WGC стоп. Кроме того, `SW_HIDE` скрывает окно из панели задач и может нарушить WGC-хэндл.
- **Свой системный трей / backdrop для показа поверх** — вне scope v1 (FR-020).
- **Отдельный класс `GameWindowHider` вне `WindowTracking`** — отклонено: логически принадлежит `WindowTracking` (управление позицией окна игры); размещение там согласуется с `IGameWindowTracker` (обнаружение) + `IGameWindowController` (управление позицией).

**Последствия**:
- `WidgetWindow.xaml`: игровой скин применён, заголовок-плашка «TBHStats», пергаментная панель статов, все стили из `GameWidgetStyles.xaml`. Хардкод цветов в разметке отсутствует.
- `WidgetWindow.xaml.cs`: `ApplyWidgetSettings` применяет `OverlappedPresenter.IsAlwaysOnTop = ws.AlwaysOnTop` (ранее принудительно `false`); чекбокс `AlwaysOnTopCheckBox` синхронизируется через флаг `_applyingSettings`; при закрытии — Restore уведённого окна игры.
- `Composition.cs`: `services.AddSingleton<IGameWindowController, GameWindowController>()`.
- Нет изменений в `WidgetSettings` (поле `AlwaysOnTop` уже есть), схеме БД и EF-конфигурации (миграция не нужна).
- Документация: ARCHITECTURE.md §7 (скин, чекбокс, кнопка); этот ADR-026.
