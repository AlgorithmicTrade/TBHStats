# Data Model: TBHStats

**Feature**: `001-tbh-stats-helper` | **Date**: 2026-05-31
**Source**: [spec.md](./spec.md) Key Entities + FR-001…FR-021 | **Storage**: SQLite (EF Core)

Принципы модели:
- Справочные сущности (`ChestType`, `HeroClass`, `Act`, `Difficulty`) — **данные, а не enum-в-коде** → новые механики добавляются записями (FR-021).
- История ссылается на **id справочников**, а не на захардкоженные значения → старые данные валидны после расширений (FR-013/SC-010).
- OCR-производные значения снабжены флагом достоверности; недостоверное не персистится (FR-005/FR-010).

## Доменные сущности

### Stage — этап
| Поле | Тип | Правила |
|------|-----|---------|
| `Id` | int (PK) | |
| `ActId` | int (FK → Act) | |
| `DifficultyId` | int (FK → Difficulty) | |
| `Number` | int | 1..10 (текущая структура) |
| — | — | **Уникальность**: (`ActId`,`DifficultyId`,`Number`) — один и тот же номер на разных актах/сложностях = разные этапы (Edge Case спеки) |

Текущее пространство: 3×2×10 = 60; сидируется из конфига, расширяемо. Обозначение «акт-этап» (1-1…3-10).

### HeroSnapshot — снимок героя (value object)
Встраивается в `StageRun` (owned entity), отдельной таблицы не требует.
| Поле | Тип | Правила |
|------|-----|---------|
| `HeroClassId` | int (FK → HeroClass) | |
| `Level` | int | ≥1 |
| `Damage` | long | ≥0; Attack Damage из раздела Status |

Контекст забега: старые данные с другим уроном не путаются с новыми (Edge Case «респек»). **Прокси силы отряда (уточнение 2026-05-31)**: `HeroSnapshot` — единственный доступный в v1 контекст силы; `Level`+`Damage` отражают уровень и совокупный эффект экипировки/части рун **выбранного** героя. Предметы как отдельные статы, раздел Runes и герои 2–3 отряда в v1 **не считываются** (границы v1 — «Game UI Map»); руны на дроп золота/частоту сундуков не отражаются в `Damage`. Поэтому recency-aware агрегация (см. `StageAggregate`) опирается на свежее окно как лучший практический способ учесть рост силы, а ограничение зафиксировано в spec.md Assumptions.

### StageRun — забег этапа (основная запись истории)
| Поле | Тип | Правила |
|------|-----|---------|

Производные (не хранятся, вычисляются): `GoldPerHour = GoldGained / DurationSeconds * 3600`, аналогично XP и сундуки/час.

### StageAggregate — агрегат этапа (материализованный кэш, recency-aware)
| Поле | Тип | Правила |
|------|-----|---------|
| `StageId` | int (PK, FK → Stage) | |
| **All-time (вся история, справка/тренды)** | | |
| `RunCount` | int | число учтённых (не partial) забегов всего |
| `AvgGoldPerHour` / `BestGoldPerHour` | double | (FR-008) по всей истории |
| `AvgXpPerHour` / `BestXpPerHour` | double | по всей истории |
| `AvgDurationSeconds` / `BestDurationSeconds` | double/int | по всей истории |
| `ChestRatePerHour` | map ChestTypeId→double | темп сундуков по типам, вся история |
| **Recent window (свежее окно — основа ранжирования/рекомендации)** | | |
| `RecentRunCount` | int | число non-partial забегов в окне (≤ `OptimizationProfile.RecentWindowSize`) |
| `RecentAvgGoldPerHour` / `RecentBestGoldPerHour` | double | по последним N non-partial забегам |
| `RecentAvgXpPerHour` / `RecentBestXpPerHour` | double | по окну |
| `RecentAvgDurationSeconds` / `RecentBestDurationSeconds` | double/int | по окну |
| `RecentChestRatePerHour` | map ChestTypeId→double | темп сундуков по окну |
| **Power-context окна (прокси силы отряда)** | | |
| `RecentHeroLevelMin` / `RecentHeroLevelMax` | int? | диапазон уровня выбранного героя в забегах окна |
| `RecentHeroDamageMin` / `RecentHeroDamageMax` | long? | диапазон урона (Attack Damage) в забегах окна |
| `UpdatedAtUtc` | DateTime | |

**Recency-aware (уточнение 2026-05-31)**: добыча зависит от силы отряда (уровни/предметы/руны/сложность); сила растёт со временем, поэтому усреднение по **всей** истории смешивает забеги разной силы и искажает рекомендацию. Решение: ранжирование и рекомендация (FR-009/FR-017/FR-019) ведутся по **свежему окну** (`Recent*`) — последним `OptimizationProfile.RecentWindowSize` non-partial забегам (дефолт 10), что отражает текущую силу. All-time-поля сохраняются для справки и трендов (US3). Power-context (`RecentHeroLevel/Damage Min/Max`) — прокси силы по **выбранному герою** (предметы, руны, герои 2–3 в v1 не считываются — см. Assumptions); экран сравнения показывает, при какой силе измерены числа, и помечает «устаревшие» забеги, чьё окно было при заметно меньшей силе, чем текущая.

Пересчитывается при добавлении/изменении `StageRun` (T038). Можно вычислять на лету (данных мало), материализация — оптимизация для экрана сравнения (SC-005). Добавление recent/power-полей — EF-миграция без потери истории (FR-013).

## Конфигурация / состояние приложения

### OptimizationProfile — профиль оптимизации
| Поле | Тип | Правила |
|------|-----|---------|
| `SelectedMetric` | enum {`GoldPerHour`,`XpPerHour`} | по умолчанию `GoldPerHour` (FR-009/Q2=A) |
| `RecentWindowSize` | int | размер свежего окна агрегации (число последних non-partial забегов на этап); дефолт 10; ≥1 |
| `Scope` | enum {`Recent`,`AllTime`} | какой набор агрегатов использует ранжирование/рекомендация; дефолт `Recent` (при текущей силе) |

Определяет сортировку и рекомендацию (FR-017/FR-019). v1 — две метрики (золото/час, опыт/час). `RecentWindowSize`/`Scope` управляют recency-aware агрегацией (уточнение 2026-05-31): по умолчанию ранжируем по свежему окну (текущая сила отряда), `AllTime` — для справки. Добавление полей — EF-миграция без потери истории (FR-013).

### RoiCalibration — калибровка областей считывания
| Поле | Тип | Правила |
|------|-----|---------|

## Состояния захвата (capture state machine) — FR-001/FR-005

```
NotFound ──(найдено окно TBH)──▶ Capturing
Capturing ──(окно свёрнуто/закрыто)──▶ Waiting        (НЕ ошибка; показываем последние достоверные)
Waiting ──(окно снова видимо)──▶ Capturing            (авто-возобновление ≤5с, SC-008)
Capturing ──(низкая уверенность OCR)──▶ Capturing     (точку отбрасываем, без записи; FR-005/010)
любое ──(процесс игры завершился)──▶ NotFound
```

Перекрытое окно остаётся в `Capturing` (WGC захватывает фон — R1); `Waiting` только для свёрнутого/закрытого.

**Детекция активной вкладки (FR-002a)**: на каждом кадре в `Capturing` сначала распознаётся название активной вкладки (ROI `activeTab`). Затем читаются только те поля, чей источник доступен: `MainZone` всегда + поля той вкладки, что сейчас активна. Если активная вкладка не определена достоверно — поля с `Source=Tab` пропускаются (точки отбрасываются), `MainZone`-поля продолжают читаться.

**Детекция завершения этапа (FR-002, сегментация забегов)**: прогрессбар + появление/убийство босса этапа в MainZone отмечают конец этапа; при этом фиксируется `stageTime` и закрывается `StageRun` (прирост золота/опыта/сундуков за интервал забега). Босс этапа = шанс синего сундука; босс акта (этап «-10») = шанс красного.

### Основная зона (MainZone) — всегда видима
- **Прогрессбар этапа** (`stageProgress`) — прогресс прохождения текущего этапа; в конце появляется **босс этапа**, убийство которого = прохождение этапа. Главный сигнал события завершения этапа (сегментация забегов).
- **Время прохождения этапа** (`stageTime`) — появляется в конце этапа (после убийства босса).
- **Сундуки** (`chest:*`) — заполняемые «точки» под иконкой каждого типа = число полученных; транзиентно (обнуляются при открытии).
- **Следующая локация** (`nextLocation`) — слева; current+1 (с переносом «-10 → следующий акт -1»); отсутствует на максимально открытой локации.

### Механика выпадения сундуков (контекст для учёта)
- **Коричневый (обычный)** — падает с шансом с **любого монстра на любом этапе**.
- **Синий (редкий)** — шанс с **босса в конце каждого этапа**.
- **Красный (легендарный)** — шанс с **босса акта** (этап 10 каждого акта: 1-10, 2-10, 3-10).

Следствие для аналитики: красный сундук возможен только на «-10» этапах, синий — на любом этапе (босс), коричневый — везде. Это контекст для интерпретации темпов сундуков по этапам (не меняет формулы, но объясняет распределение).

### Герои
Отряд из **3 героев**; статистика/экипировка показываются для **выбранного** героя. Состав отряда (Composition) в v1 не требуется. `HeroSnapshot` фиксирует контекст выбранного героя на момент забега.

## Валидация (сводка правил)

- Уникальность `Stage(ActId,DifficultyId,Number)`.
- `DurationSeconds > 0`; приросты ≥ 0. Накопленный итог сундуков забега (`StageRunChest.Count`) ≥ 0 и неубывает; отображаемые точки MainZone транзиентны (обнуление при открытии = не потеря).
- Накопительные золото/опыт монотонны в пределах этапа → нарушение = отброс точки (R4).
- В агрегаты «Best/Avg» (all-time и свежее окно) идут только `IsPartial=false` забеги (FR-010).
- **Recency-aware ранжирование (уточнение 2026-05-31)**: рекомендация и сортировка этапов считаются по **свежему окну** (`Recent*` — последние `OptimizationProfile.RecentWindowSize` non-partial забегов), а не по all-time — т.к. добыча зависит от растущей силы отряда. Power-context окна (`RecentHeroLevel/Damage Min/Max`) — прокси силы по выбранному герою; забеги при заметно меньшей силе, чем текущая, помечаются «устаревшими» на экране сравнения (не исключаются из истории, но не задают рекомендацию).
- Темпы считаются только по `MetricSample.IsReliable=true` интервалам (FR-005a).
- **EXP в пределах уровня**: `MetricSample.Xp` — это EXP внутри текущего уровня (сбрасывается при level-up). Опыт/час вычисляется по дельте с учётом `HeroLevel`: при инкременте уровня к приросту добавляется «добор» до полного предыдущего уровня (нужен `xpToLevel` предыдущего уровня), а не трактуется как убыль. Поэтому `MetricSample` хранит и `Xp`, и `XpToLevel`, и `HeroLevel`.
- **Транзиентный счётчик сундуков**: `MetricSample.Chests` — мгновенное число точек (растёт при выпадении, падает к 0 при открытии). «Получено за забег» (`StageRunChest.Count`) = сумма положительных дельт счётчика; падение к 0 = открытие, НЕ потеря (не уменьшает накопленный итог). Это снимает прежнее упрощение «счётчики неубывают»: неубывает именно накопленный итог забега, а не отображаемое число точек.
- Любое OCR-значение проходит confidence-порог + sanity до персиста (FR-005/010).
