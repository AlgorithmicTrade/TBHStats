# Phase 0 Research: TBHStats

**Feature**: `001-tbh-stats-helper` | **Date**: 2026-05-31
**Goal**: разрешить технические неизвестные плана, зафиксировать library-first решения.

> Принцип: предпочитаем встроенные платформенные API (WinRT) сторонним зависимостям, где они закрывают потребность (конституция, Принцип III).

---

## R1. Захват конкретного окна игры (терпимый к перекрытию, следящий за окном)

**Решение**: **Windows.Graphics.Capture (WGC)** с таргетингом по **HWND** через interop (`IGraphicsCaptureItemInterop.CreateForWindow`).

**Обоснование**:
- WGC через DWM/DXGI отдаёт GPU-текстуру конкретного окна по HWND и **захватывает окно, даже когда оно перекрыто/в фоне** (обходит Z-order) — это прямое покрытие FR-005 («ожидание, не ошибка» при перекрытии больше не нужно из-за невозможности захвата; ожидание остаётся только для свёрнутого/закрытого окна).
- Захват по HWND автоматически «следует» за окном при перемещении/ресайзе → основа для FR-005b.
- Встроено в Windows 10 1903+/Windows 11, без сторонних зависимостей.

**Альтернативы рассмотрены**:
- `PrintWindow` (GDI, флаг `PW_RENDERFULLCONTENT`) — работает для фоновых окон, но не для всех рендереров (часто чёрный кадр у GPU-ускоренных приложений). Оставляем как аварийный fallback, не основной путь.
- BitBlt со скриншота экрана — ломается при перекрытии и привязан к экрану, а не к окну. ❌ противоречит FR-005/005b.
- DXGI Desktop Duplication — это весь экран/монитор, не окно. ❌

**Library/API**: `Windows.Graphics.Capture` + `Windows.Graphics.Capture.Interop` (WinRT, встроено). Для unpackaged-доступа — проекции CsWinRT (см. R6). Свёрнутое окно (`IsIconic`) не имеет валидной поверхности → состояние «ожидание» до восстановления (FR-005).
**Источник**: [Windows.Graphics.Capture — Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture?view=winrt-26100)

## R2. OCR игровых значений

**Решение**: **Windows.Media.Ocr** (`OcrEngine.TryCreateFromUserProfileLanguages`/`TryCreateFromLanguage`) как основной движок; **Tesseract — fallback**, если на реальном шрифте игры точность недостаточна.

**Обоснование**:
- Встроен в Windows, **0 сторонних зависимостей**, GPU/CPU-оптимизирован, хорошо справляется с чистыми UI-цифрами/латиницей.
- Принимает `SoftwareBitmap` — кадр WGC конвертируется напрямую, без диска.
- Возвращает слова с bounding box → можно сопоставлять с ROI и оценивать достоверность по геометрии.

**Альтернативы**:
- **Tesseract** (`TesseractOCR`/`tesseract.net`): ~95–99% на чистом тексте, но требует нативные бинарники + traineddata, и часто проблемы с пунктуацией. Точнее настраивается под цифры (`tessedit_char_whitelist=0123456789.,KMB`), поэтому держим как fallback для «трудных» ROI.
- PaddleOCR/Surya — точнее на сложных сценах, но тяжёлый рантайм (Python/ONNX), избыточно для коротких числовых строк. ❌

**Риск/валидация**: фактическая точность на конкретном шрифте TBH — **эмпирический вопрос**, проверяется на реальных скриншотах в фазе реализации (Capture.Tests на фикстурах-изображениях). Митигировано: confidence-порог + sanity-проверки значений (R4), per-ROI выбор движка через конфиг.
**Источник**: [Windows.Media.Ocr — Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine?view=winrt-26100), [Tesseract](https://github.com/tesseract-ocr/tesseract)

## R3. Привязка областей считывания к окну (независимость от экрана/масштаба) — FR-005b

**Решение**: ROI хранятся как **нормализованные доли клиентской области окна** (`x,y,w,h ∈ [0..1]`), а не в пикселях экрана. На каждом кадре известны размеры клиентской области (из WGC item size) → ROI разворачивается в пиксели текущего кадра.

**Обоснование**:
- Кадр WGC — это содержимое окна, его размер меняется вместе с окном. Доли инвариантны к размеру/масштабу/DPI/монитору → автоматическое следование (FR-005b) без перекалибровки.
- Калибровка пользователем (FR-003) = разметка прямоугольников поверх захваченного кадра → сохраняем как доли.

**Альтернативы**: абсолютные экранные координаты — ломаются при любом перемещении/масштабе. ❌
**Library**: собственная (тонкая, <50 строк математики), доменная — в `TBHStats.Capture/Roi`.

## R4. Парсинг чисел и устойчивость значений

**Решение**: собственный парсер сокращённого игрового формата (`1.2K`, `3.4M`, `1,234`, `5B`) + слой sanity-проверок.

**Правила**:
- Суффиксы K/M/B/T → множители; десятичный разделитель и группировка нормализуются.
- **Монотонность накопительных значений**: золото не убывает в пределах этапа (кроме легитимной траты — см. ниже) → необъяснённое убывание трактуется как ошибка распознавания, точка отбрасывается (питает FR-010).
- **EXP** показывается в пределах уровня и обнуляется при level-up: прирост опыта считается с учётом `HeroLevel` (инкремент уровня = добор до полного предыдущего уровня + текущий EXP), а не как убыль.
- **Сундуки (точки MainZone)**: счётчик транзиентный — растёт при выпадении, падает к 0 при открытии. «Получено за забег» = сумма положительных дельт; обнуление = открытие, не потеря. Накопленный итог забега неубывает.
- **Confidence-порог**: результат OCR с низкой геометрической/словарной уверенностью или не проходящий sanity — **не записывается** (FR-005/FR-010), показывается последнее достоверное.
- **Следующая локация (MainZone)** может служить перекрёстной проверкой текущего этапа (current = next−1 с переносом «-10 → следующий акт -1»); отсутствие на макс. локации — норма, не ошибка.
- **Завершение этапа (MainZone)**: прогрессбар + появление/убийство босса этапа = надёжный сигнал конца этапа → фиксация `stageTime` и закрытие `StageRun`. Предпочтительнее, чем угадывать по сбросу значений. Босс этапа ↔ синий сундук; босс акта («-10») ↔ красный.

**Обоснование**: idle-числа быстро уходят в сокращённый формат; без корректной интерпретации темпы будут мусором. Логика чисто доменная → `TBHStats.Core/Parsing`, 100% покрывается unit-тестами (реальные строки, без моков).
**Library**: кастом (простая логика <100 строк), переиспользуема в MAUI.

## R5. Хранилище и агрегаты

**Решение**: **SQLite через EF Core** (`Microsoft.EntityFrameworkCore.Sqlite`), файл в `%LOCALAPPDATA%\TBHStats\`.

**Обоснование**:
- Объём данных (тысячи `StageRun`) тривиален; SQLite — стандарт для локального десктоп-хранилища, переживает перезапуск/перезагрузку (FR-011, SC-004).
- EF Core: миграции (расширение схемы под новые механики без потери истории — FR-013/FR-021), LINQ-агрегации (средние/лучшие/темпы по этапу — FR-008), nullable-аннотации (Принцип V).
- Конфиг игровых механик (типы сундуков/классы/этапы) — отдельная таблица + сидинг из декларативного описания → новые сущности добавляются данными, не схемой.

**Recency-aware агрегация (уточнение 2026-05-31)**: добыча зависит от растущей силы отряда (уровни/предметы/руны; сложность — измерение этапа), поэтому усреднение по всей истории искажает рекомендацию (смешивает забеги слабого и сильного отряда). Решение: `StageAggregate` материализует И all-time, И **свежее окно** (последние `OptimizationProfile.RecentWindowSize` non-partial забегов, дефолт 10) + power-context (диапазон уровня/урона выбранного героя в окне). Ранжирование/рекомендация (FR-009) — по свежему окну (текущая сила); all-time — справка/тренды. Реализуемо штатным EF Core (оконная выборка `OrderByDescending(CompletedAtUtc).Take(N)` + LINQ-агрегации); миграция добавляет поля без потери истории (FR-013). Прокси силы — выбранный герой; руны/предметы/герои 2–3 в v1 не читаются (документированное ограничение, spec.md Assumptions).

**Альтернативы**: LiteDB (документная, но слабее по миграциям/агрегации), сырой JSON-файл (нет конкурентной записи и индексов). ❌ для растущей истории. По агрегации: power-band-сегментация (тегирование забегов «сигнатурой силы») отклонена в пользу recency-окна — проще, робастнее и не требует чтения непрочитываемых в v1 факторов (руны/предметы).
**Тесты**: на реальном временном SQLite-файле (НЕ in-memory-мок БД), чтобы проверять реальную SQL-семантику (конституция/quality-rules).
**Источник**: EF Core SQLite provider (Microsoft Learn / NuGet).

## R6. Доступ к WinRT (WGC/OCR) из .NET 8 desktop и формат поставки

**Решение**: целевой TFM с проекциями WinRT — `net8.0-windows10.0.22621.0` (через `Microsoft.Windows.SDK.Net.Ref`/CsWinRT). Поставка — **packaged (MSIX)** по умолчанию для надёжного доступа к WinRT и автообновлений; unpackaged поддерживается, но с известными оговорками.

**Обоснование**:
- WGC и Windows.Media.Ocr — WinRT; из .NET 8 доступны через CsWinRT-проекции при правильном `TargetPlatformVersion`.
- Unpackaged WinUI 3 на .NET 8 работает, но у части WinRT-API есть сноски «нюансы вне packaged»; MSIX снимает риски идентичности приложения и доступа к API.

**Альтернатива**: unpackaged + self-contained (проще распространять одним .exe, но требует установленного .NET 8 desktop runtime и тщательной проверки WinRT-вызовов). Оставляем как опцию для «portable»-сборки.
**Источники**: [WindowsAppSDK Discussion #1615](https://github.com/microsoft/WindowsAppSDK/discussions/1615), [microsoft-ui-xaml #8463](https://github.com/microsoft/microsoft-ui-xaml/issues/8463)

## R7. UI-оболочка виджета (оверлей, topmost, перемещаемый, ≤15% экрана)

**Решение**: **WinUI 3** (Windows App SDK) как основной UI; **WPF — задокументированный fallback**, если перетекающая прозрачность/`Topmost`-оверлей в WinUI 3 окажутся проблемными для конкретного дизайна виджета.

**Обоснование**:
- WinUI 3 — современный Fluent-стек, MVVM (CommunityToolkit.Mvvm), один рантайм с остальным .NET 8.
- Историческая слабость WinUI 3 — per-pixel-прозрачность/click-through оверлеи; WPF (`AllowsTransparency`, `Topmost`, `WS_EX_LAYERED`) для этого зрелее. Поэтому fallback зафиксирован заранее, чтобы не блокировать P1.
- Требования: перемещаемость, опц. «поверх окон» (FR-015), сохранение позиции/размера (FR-016), компактность ≤15% (SC-006) — выполнимы в обоих.

**Решение по риску**: оверлей-оболочка изолирована в `TBHStats.App/Views` за тонким интерфейсом окна-виджета → смена WinUI↔WPF не затрагивает Core/Capture/Data.

## R8. Графики (тренды) — FR-018 (P3)

**Решение**: **LiveCharts2** (`LiveChartsCore.SkiaSharpView.WinUI`).

**Обоснование**:
- Официальная поддержка WinUI 3, единственная зависимость — SkiaSharp; качественные анимации и интерактивность (тултипы по точкам — US3 сценарий 2).
- Один API на все .NET UI → переиспользуемо, если Android-клиент будет на MAUI.

**Альтернатива**: **ScottPlot** (отличен для научных/плотных данных, быстрый), но интерактивность/стилизация под лёгкий виджет у LiveCharts2 удобнее. Держим как замену при проблемах со Skia-рендером в оверлее.
**Источники**: [LiveCharts2](https://github.com/Live-Charts/LiveCharts2), [WinUI3 + LiveCharts2 sample](https://github.com/XamlBrewer/XamlBrewer.WinUI3.LiveChart2.Sample)

## R9. Расширяемость игровых механик — FR-021

**Решение**: декларативный **GameMechanicsConfig** (типы сундуков, классы, акты/сложности/этапы) в `TBHStats.Core/Mechanics`, сериализуемый (встроенный default + переопределение из файла/БД). Новый элемент (4-й сундук, новый класс) = запись в конфиге + ROI в калибровке, **без правки доменных типов и схемы БД** (ChestType/Class — справочные сущности-данные, не enum'ы-в-коде).

**Обоснование**: прямое выполнение FR-021/SC-010; история валидна, т.к. ссылается на справочные id, а не на захардкоженные enum'ы.

## R11. Детекция активной вкладки (FR-002a/002b)

**Решение**: распознавать **название активной вкладки** через тот же OCR (R2) в выделенной ROI (`activeTab`) и матчить с `Tab.RecognitionText` из конфига (нормализация регистра/пробелов, при необходимости — fuzzy/расстояние Левенштейна для устойчивости к шуму). Поля привязаны к источнику (`MainZone`/конкретная вкладка); читаются только доступные при текущей активной вкладке.

**Обоснование**:
- Названия вкладок «чётко читаемы» (со слов пользователя) → надёжный текстовый матч, точнее числового OCR.
- Никакого автопереключения (observe-only): обновление значений вкладок — оппортунистическое, когда игрок сам открыл вкладку (FR-002b).
- Подвкладки вне объёма; список вкладок (сейчас 8) расширяем через `Tab` в конфиге (FR-021).

**Альтернативы**: детекция по подсветке/позиции активной вкладки (пиксели) — хрупко к теме/масштабу; ❌ в пользу текстового распознавания названия.
**Library**: переиспользует `IOcrReader`; логика матчинга — доменная (`TBHStats.Core`).

## R10. Задел под Android (FR-020) — без реализации в v1

**Решение**: вынести всю не-UI доменную логику в `TBHStats.Core` (без WinRT/UI-зависимостей) → переиспользуема в **.NET MAUI**. Данные хранить так, чтобы их мог отдать будущий локальный API (`TBHStats.Remote`, ASP.NET minimal API, привязка к localhost/LAN + парный токен).

**Обоснование**: MAUI и десктоп делят .NET/C# и `Core` → реальное переиспользование логики (преимущество выбранного стека). В v1 создаём только границы (интерфейсы репозиториев/DTO), сам сервер не поднимаем (Out of Scope спеки).

## R12. Инструментарий «нехрупких» UI-тестов поверх живой игры (FR-022…FR-027)

**Решение**: **.NET-харнесс на xUnit** + **FlaUI** (UIA + нативный ввод/окна) + **визуальная локализация элементов через переиспользование слоя захвата** (WGC-кадр + OCR названий разделов/кнопок → bounding box в координатах окна) + **инъекция кликов SendInput** (через FlaUI) в **случайную точку в пределах элемента** со **случайной ограниченной задержкой** и плавным перемещением курсора. Отдельный проект `TBHStats.UiTests`, не входит в поставку.

**Почему НЕ Playwright**: Playwright — для браузеров/веба; TBH — нативный десктоп (нет API, рендер на canvas/DirectX → UIA-дерево обычно отсутствует). Playwright применим только если игра окажется **Electron с CDP** — это надо проверить эмпирически (запустить игру, проверить тип процесса/наличие remote-debug). Если так — возможен альтернативный путь через CDP, но базовый план — визуальный.

**Почему FlaUI, а не WinAppDriver/Appium**: WinAppDriver слабо поддерживается; FlaUI — активный .NET-стек, прямой доступ к UIA и нативному вводу, естественен для нашего проекта. Элементы, не видимые UIA (игровой рендер), локализуются визуально через уже имеющийся OCR/ROI (Capture) — двойная выгода: тест заодно валидирует продуктовый слой распознавания.

**Нехрупкость/детерминизм**: ассерты по **распознанному состоянию** (активный раздел по названию), а не по пикселям; **ожидание** появления состояния (poll-with-timeout) перед действием/проверкой; повтор серии прогонов даёт одинаковый вердикт (SC-012). Человекоподобность: точка клика — случайна в границах элемента (не центр), задержки — случайны в диапазоне, движение мыши — с easing.

**Безопасность (carve-out конституции)**: харнесс — отдельный QA-компонент, продукт остаётся observe-only. Запрещённый список действий (не нажимать): апгрейды Runes, крафт/переработка Cube, перемещения Stash, торговля Trade ship — только безопасная навигация/просмотр (FR-026). Guard-проверка в харнессе блокирует клики по координатам запрещённых элементов.

**Открытый эмпирический пункт**: тип приложения TBH (нативное vs Electron) — проверяется при первом запуске харнесса; влияет лишь на наличие альтернативного CDP-пути, базовый визуальный подход работает в любом случае.

**Library**: FlaUI (`FlaUI.Core`, `FlaUI.UIA3`), переиспользование `TBHStats.Capture` (OCR/ROI), xUnit.
