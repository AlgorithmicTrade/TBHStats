# Feature Specification: TBHStats — помощник по статистике Task Bar Hero

**Feature Branch**: `001-tbh-stats-helper`
**Created**: 2026-05-31
**Status**: Draft
**Input**: User description: "Для новой игры Task Bar Hero (Idle RPG, виджет на рабочем столе Windows 11) создать помощника по статистике — виджет на рабочем столе. Программа считывает из окна запущенного TBH: золото (текущее и получаемое), опыт (текущий и получаемый), время прохождения этапа (в секундах в конце этапа), класс героя, уровень героя, урон героя, текущий этап (3 акта × 3 сложности × 10 этапов), момент прохождения этапа. На основе данных показывает статистику (опц. графики): золото/час, опыт/час, время этапа; сравнивает с историей по другим этапам и выбирает оптимальный этап для фарма. В дальнейшем — расширение до Android-приложения для удалённого просмотра статистики."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Живая статистика текущего забега (Priority: P1)

Игрок запускает Task Bar Hero и рядом — виджет-помощник. Помощник автоматически находит запущенную игру, считывает текущие значения (золото, опыт, класс/уровень/урон героя, текущий этап) и в реальном времени показывает темп добычи: **золото/час** и **опыт/час** для текущего этапа, а также время прохождения этапа. Игрок видит, насколько эффективен текущий этап, не отвлекаясь от игры.

**Why this priority**: Это минимально жизнеспособный продукт. Даже без истории и рекомендаций игрок сразу получает ценность — понимает реальную скорость фарма «здесь и сейчас», которую игра сама в явном виде (за час) не показывает.

**Independent Test**: Запустить виджет рядом с работающей игрой на известном этапе, подождать несколько циклов добычи и убедиться, что показанные золото/час и опыт/час соответствуют наблюдаемому приросту значений в игре, а класс/уровень/урон/этап отображены корректно.

**Acceptance Scenarios**:

1. **Given** запущена игра TBH на этапе Акт 1 / Нормал / Этап 5, **When** помощник стартует, **Then** в течение нескольких секунд виджет показывает текущее золото, опыт, класс, уровень, урон, идентификатор этапа, количество сундуков по типам и вычисленные золото/час, опыт/час, сундуки/час.
2. **Given** помощник работает и идёт добыча, **When** значения золота/опыта/сундуков в игре растут, **Then** темпы пересчитываются и обновляются без действий пользователя.
3. **Given** герой завершает этап (убит босс в конце прогрессбара), **When** игра показывает время прохождения этапа, **Then** помощник фиксирует завершение и время, привязывая их к текущему этапу.
4. **Given** игра не запущена, **When** пользователь открывает помощник, **Then** виджет явно сообщает «игра не найдена» и ждёт её появления, не падая.
5. **Given** помощник считывает данные, **When** окно игры перекрывается другим окном, **Then** помощник не выдаёт ошибку, показывает статус ожидания и автоматически возобновляет считывание после возврата видимости окна; темпы не занижаются за период перекрытия.

### User Story 2 — История этапов и выбор оптимального для фарма (Priority: P2)

По мере игры помощник накапливает историю по каждому из этапов (акт × сложность × этап). Для каждого этапа он хранит измеренные показатели: золото/час, опыт/час, среднее/лучшее время прохождения. Игрок открывает сравнение и видит таблицу всех пройденных этапов, отсортированную по эффективности, а помощник **подсвечивает оптимальный этап для фарма** согласно выбранной цели оптимизации. Это позволяет осознанно выбирать, где фармить, вместо догадок.

**Why this priority**: Это главная аналитическая ценность продукта («ради чего»). Но она надстраивается над P1: без живого захвата и накопленной истории сравнивать нечего.

**Independent Test**: Сыграть на нескольких разных этапах так, чтобы по каждому появились данные, открыть экран сравнения и убедиться, что этапы ранжированы по выбранной метрике, а рекомендованный этап действительно имеет наилучший измеренный показатель.

**Acceptance Scenarios**:

1. **Given** в истории есть данные минимум по двум этапам, **When** игрок открывает сравнение, **Then** показывается список этапов с золото/час, опыт/час и временем прохождения, отсортированный по выбранной метрике.
2. **Given** накоплена история, **When** игрок запрашивает рекомендацию, **Then** помощник называет конкретный этап (акт/сложность/этап) как оптимальный для фарма и поясняет, по какому показателю он лучший.
3. **Given** игрок переключает цель оптимизации (золото/час ↔ опыт/час), **When** применяется новая цель, **Then** ранжирование и рекомендация пересчитываются под выбранную цель.
4. **Given** история пуста (первый запуск), **When** игрок открывает сравнение, **Then** помощник сообщает, что данных пока нет, и предлагает поиграть для их накопления.
5. **Given** помощник перезапущен, **When** он стартует снова, **Then** ранее накопленная история этапов доступна (сохраняется между сессиями).

### User Story 3 — Визуализация трендов графиками (Priority: P3)

Игрок открывает графики и видит динамику ключевых показателей во времени: как менялись золото/час и опыт/час, как уменьшалось время прохождения этапа по мере роста уровня/урона героя. Это помогает заметить, когда этап «выработан» (рост замедлился) и пора двигаться дальше.

**Why this priority**: Усиление аналитики — приятное, но не обязательное для основной ценности. Само по себе бесполезно без данных из P1/P2, поэтому ниже приоритетом.

**Independent Test**: Имея историю по этапу за некоторый период, открыть график и убедиться, что линии золото/час, опыт/час и времени прохождения отражают реально записанные точки и корректно подписаны по времени.

**Acceptance Scenarios**:

1. **Given** по этапу накоплены данные за несколько забегов, **When** игрок открывает график этого этапа, **Then** отображаются тренды золото/час, опыт/час и времени прохождения по времени.
2. **Given** график открыт, **When** игрок наводит на точку, **Then** показываются точные значения и момент времени.

### Edge Cases

- **Игра закрылась во время сессии** — помощник перестаёт получать обновления, помечает данные как устаревшие и продолжает работать, ожидая возврата игры; накопленная история не теряется.
- **Окно игры перекрыто/свёрнуто/невидимо** — помощник **не выдаёт ошибку**, а ждёт, пока окно снова станет видимым, и автоматически возобновляет считывание; периоды недоступности не учитываются в темпах как «нулевая добыча».
- **Окно игры перемещено/изменён размер/перенесено на другой монитор** — считывание продолжается без ручной перенастройки (привязка к окну, а не к экрану).
- **Значение временно нечитаемо** (всплывающее окно игры, курсор поверх числа) — помощник не записывает «мусорные» значения, показывает последние достоверные и метку устаревания.
- **Нужная вкладка не открыта** — значения с этой вкладки не обновляются; помощник показывает последнее достоверное с пометкой устаревания и автоматически обновляет их, когда пользователь откроет вкладку (без ошибок и без автопереключения вкладок — observe-only).
- **Неоднозначное/нераспознанное название вкладки** — при невозможности достоверно определить активную вкладку помощник не приписывает считанные значения неверному источнику (точки отбрасываются до восстановления уверенности).
- **Сбой распознавания** (изменён масштаб/тема/шрифт игры, окно сдвинуто, перекрыто курсором/подсказкой) — при низкой уверенности распознавания значение отбрасывается, а не записывается; пользователю доступна перекалибровка областей считывания.
- **Сокращённая запись чисел** (например, «1.2K», «3.4M») — система корректно интерпретирует игровой формат больших чисел при распознавании.
- **Смена этапа во время измерения** — частичный незавершённый забег не должен искажать агрегаты этапа; неполные интервалы либо отбрасываются, либо отмечаются как частичные.
- **Первый запуск без истории** — все экраны сравнения/графиков корректно показывают «нет данных».
- **Один и тот же номер этапа на разных сложностях/актах** — это разные сущности; данные не должны смешиваться.
- **Idle-прирост, пока помощник не запущен** — добыча, происходившая без работающего помощника, не учитывается; в истории возможны пропуски, и это не должно ломать агрегаты.
- **Смена класса/респек героя** — записи привязаны к контексту героя на момент забега, чтобы старые данные с другим уроном не вводили в заблуждение.
- **Будущее изменение структуры контента игры** (новые акты/сложности сверх текущих 3 акта × 2 сложности × 10 = 60) — модель данных должна допускать расширение без потери старой истории.
- **Резкий скачок значения** (крупная награда, продажа инвентаря) — выброс не должен необоснованно завышать золото/час.
- **Сброс EXP при повышении уровня** — опыт отображается в пределах уровня (текущий / нужный до уровня) и обнуляется при level-up; опыт/час MUST вычисляться с учётом переходов уровня (инкремент уровня = «добор» до полного предыдущего уровня + текущий EXP), а не как падение значения.
- **Сброс счётчика сундуков при открытии** — полученные сундуки отображаются в основной зоне как заполняемые «точки» под иконкой каждого типа (число точек = число полученных сундуков данного типа); при открытии сундука точки исчезают (счётчик падает к 0). Поэтому «получено сундуков» MUST считаться как сумма приростов счётчика (положительных дельт), а падение к 0 трактуется как **открытие, а не потеря** (не уменьшает накопленный итог забега).
- **Следующая локация на максимально открытом этапе** — в основной зоне слева показывается следующая доступная локация (для 2-5 → «2-6», для 2-10 → «3-1»); если игрок на максимально открытой локации, она **не отображается** — система не должна считать её отсутствие ошибкой.

## Requirements *(mandatory)*

### Functional Requirements

**Обнаружение и захват данных**

- **FR-001**: Система MUST автоматически определять, запущена ли игра Task Bar Hero, и находить источник её данных.
- **FR-002**: Система MUST считывать из запущенной игры следующие значения: текущее золото, текущий опыт, время прохождения этапа (в секундах, отображаемое в конце этапа), класс героя, уровень героя, урон героя, идентификатор текущего этапа (акт + сложность + номер этапа), событие/момент завершения этапа, а также **количество полученных сундуков по типам** (на момент написания типов три: базовый/коричневый, редкий/синий, легендарный/красный). Набор типов сундуков не зашит жёстко и определяется конфигурацией игровых механик (см. FR-021).
- **FR-002a**: Окно игры состоит из **основной игровой зоны** и **набора именованных разделов** (на момент написания их 9: Hero, Stash, Status, Runes, Cube, Portal, Settings, Trade ship, Mail Box; у каждого чётко читаемое название; у части разделов есть подвкладки — в текущем объёме не учитываются). Система MUST определять, **какой раздел сейчас открыт**, считывая названия разделов, и MUST знать текущий активный раздел.
- **FR-002b**: Каждое считываемое значение MUST быть привязано к своему **источнику** — основной игровой зоне или конкретной вкладке. Система MUST считывать значение только когда его источник фактически отображается (нужная вкладка открыта или это всегда видимая зона). Если вкладка со значением не открыта, система **не выдаёт ошибку и не выдумывает значение**, а сохраняет последнее достоверное (согласовано с FR-005/FR-005a) и обновляет его при следующем открытии этой вкладки пользователем. Набор вкладок и привязки «значение → источник» задаются конфигурацией игровых механик (FR-021), без правок кода.
- **FR-003**: Источник данных — **визуальный захват с экрана**: система считывает значения, распознавая числа и текст с экранного виджета запущенной игры (захват области окна + распознавание). Машиночитаемого файла/API у игры не предполагается. Система MUST позволять пользователю задать/откалибровать области экрана, откуда считываются конкретные значения, и MUST устойчиво обрабатывать ситуации, когда распознавание ненадёжно (низкая уверенность → значение не записывается, см. FR-005).
- **FR-004**: Система MUST периодически обновлять считываемые значения, пока игра работает (по умолчанию — короткий регулярный интервал опроса, см. Assumptions).
- **FR-005**: Чтение с экрана MUST быть устойчивым (не «хрупким»). Когда окно игры перекрыто другим окном, свёрнуто или временно невидимо, система **не выдаёт ошибку**, а спокойно **ожидает**, пока окно снова станет визуально доступным, и автоматически возобновляет считывание. Пока окно недоступно, система показывает последние достоверные данные с пометкой устаревания и не записывает недостоверные значения.
- **FR-005a**: Статистика MUST пересчитываться **только по фактически доступным (достоверно считанным) значениям**: периоды недоступности окна не учитываются как «нулевая добыча» и не занижают темпы (золото/час, опыт/час, сундуки/час). Темпы вычисляются по интервалам, когда значения действительно наблюдались.
- **FR-005b**: Система MUST быть **независима от конфигурации системы и расположения окна**: она отслеживает именно окно игры, а не фиксированные координаты экрана, и MUST корректно работать при любом положении окна, любом его размере/масштабе, на любом мониторе и при любом разрешении/масштабировании рабочего стола. При перемещении или изменении размера окна игры считывание MUST продолжаться без ручной перенастройки (области считывания привязаны к окну игры, а не к экрану).

**Вычисление показателей**

- **FR-006**: Система MUST вычислять для текущего этапа золото/час, опыт/час и **темп получения сундуков по типам** (сундуки/час и количество за забег) на основе наблюдаемого прироста значений во времени.
- **FR-007**: Система MUST фиксировать каждый завершённый забег этапа с его показателями: время прохождения, прирост золота, прирост опыта, **полученные сундуки по типам**, момент завершения, контекст героя (класс/уровень/урон) на момент забега.
- **FR-008**: Система MUST агрегировать историю по каждому этапу (акт × сложность × этап), вычисляя как минимум средние и лучшие значения золото/час, опыт/час, времени прохождения и **темпа сундуков по типам**. **Уточнение (2026-05-31)**: т.к. добыча зависит от растущей со временем силы отряда (уровни/предметы/руны; сложность — уже измерение этапа), агрегаты MUST вычисляться не только по всей истории, но и по **свежему окну** недавних забегов (последние N non-partial, N настраивается, дефолт 10), отражающему текущую силу; контекст силы (уровень/урон выбранного героя) MUST фиксироваться с каждым забегом.
- **FR-009**: Система MUST сравнивать этапы и рекомендовать оптимальный этап для фарма согласно **выбираемой пользователем цели оптимизации**: золото/час **или** опыт/час. По умолчанию активна цель «золото/час»; переключение цели меняет ранжирование и рекомендацию (см. FR-019). **Уточнение (2026-05-31)**: ранжирование и рекомендация MUST по умолчанию опираться на **свежее окно** (текущая сила отряда), а не на усреднение по всей истории, чтобы не рекомендовать этап по устаревшим данным слабого отряда; режим «вся история» доступен как справочный.
- **FR-010**: Система MUST исключать или помечать выбросы и неполные забеги, чтобы они не искажали агрегаты.

**Хранение данных**

- **FR-011**: Система MUST сохранять историю забегов и агрегаты между сессиями (данные переживают перезапуск помощника и перезагрузку ПК).
- **FR-012**: Система MUST хранить данные локально на машине пользователя и не передавать их вовне без явного включения функции удалённого доступа.
- **FR-013**: Модель данных MUST поддерживать расширение набора этапов/актов/сложностей сверх текущих 60 (3 акта × 2 сложности × 10 этапов) без потери ранее накопленной истории.

**Отображение (виджет)**

- **FR-014**: Система MUST отображать живые показатели текущего забега в виде виджета на рабочем столе Windows 11.
- **FR-015**: Виджет MUST не мешать игре (компактный, перемещаемый; режим «поверх окон» — опционально по выбору пользователя).
- **FR-016**: Система MUST сохранять положение и размер виджета между сессиями.
- **FR-017**: Система MUST предоставлять представление сравнения этапов с сортировкой по выбранной метрике и явной отметкой рекомендованного этапа.
- **FR-018**: Система SHOULD отображать тренды показателей в виде графиков (опционально, приоритет P3).
- **FR-019**: Система MUST позволять пользователю переключать цель оптимизации, влияющую на ранжирование и рекомендацию.

**Расширяемость (задел на будущее)**

- **FR-020**: Система MUST хранить захваченные данные в форме, пригодной для последующего предоставления удалённому клиенту (мобильному приложению-просмотрщику), не реализуя сам удалённый доступ в рамках данной фичи.
- **FR-021**: Система MUST допускать лёгкое подключение новых игровых механик — новых типов сундуков, новых классов героя, новых актов/сложностей/этапов, **новых вкладок (и при необходимости подвкладок)** и иных учитываемых сущностей — **через конфигурацию/описание, без переработки архитектуры**. Добавление нового элемента (например, четвёртого типа сундука, нового класса или новой вкладки) должно требовать минимальных правок (декларативное описание + область считывания + привязка к источнику), а ранее накопленная история при этом MUST сохраняться и оставаться валидной.

**UI-тестирование / аудит интерфейса (QA-харнесс)**

- **FR-022**: Проект MUST включать набор **детерминированных («нехрупких») UI-тестов** поверх **реально запущенной в системе игры**, которые автоматически аудируют интерфейс и проверяют сквозную способность помощника определять разделы, следить за окном и считывать значения.
- **FR-023**: Тестовый харнесс MUST **самостоятельно навигировать** по интерфейсу игры — переключаться между разделами и кнопками — **визуально определяя элементы** (по названию через распознавание, переиспользуя слой захвата), **без зашитых экранных координат**.
- **FR-024**: Клики MUST **эмулировать действия реального человека**: нажатие в **случайную точку в пределах границ** целевого элемента, со **случайной допустимой задержкой** между действиями (в заданном диапазоне).
- **FR-025**: **Нехрупкость/детерминизм**: тесты MUST опираться на **распознанное состояние** (а не на точные пиксели/координаты), **ожидать** появления ожидаемого состояния перед действием/проверкой, и давать **стабильный повторяемый вердикт** pass/fail по сценарию.
- **FR-026**: **Безопасность (observe-only продукта сохраняется)**: харнесс — **отдельный QA-компонент, НЕ входящий в поставляемый продукт**; включается явно, только для тестирования. Сценарии MUST **избегать действий, необратимо меняющих игровое состояние** (трата золота/апгрейд в Runes, крафт/переработка в Cube, перемещение предметов в Stash, торговля в Trade ship) — только безопасная навигация и просмотр. Продукт (runtime) **никогда** не инжектит ввод.
- **FR-027**: Тесты MUST покрывать **аудит всех 9 разделов + основной зоны**: открыть каждый раздел → подтвердить детекцию активного раздела (FR-002a) → проверить читаемость привязанных полей (FR-002b); а также следование за окном при перемещении/ресайзе (FR-005b) и устойчивость к перекрытию/сворачиванию (FR-005). Набор сценариев — в `ui-test-scenarios.md`.

### Key Entities *(include if feature involves data)*

- **Hero Snapshot (Снимок героя)**: состояние героя в момент наблюдения — класс, уровень, урон. Используется как контекст забегов.
- **Stage (Этап)**: уникальная единица контента, заданная тройкой (акт, сложность, номер этапа). Текущее пространство — 3 акта (Act 1/2/3) × 2 сложности (Normal/Nightmare) × 10 этапов = 60; обозначение «акт-этап» (1-1…3-10); модель допускает расширение.
- **Tab (Раздел/Вкладка)**: именованный раздел интерфейса игры (сейчас 9: Hero, Stash, Status, Runes, Cube, Portal, Settings, Trade ship, Mail Box), распознаётся по названию; имеет признак «активен/открыт». Источник, к которому привязаны конкретные считываемые значения. Термины «раздел» и «вкладка» здесь синонимы (top-level вкладка). Подвкладки — вне текущего объёма. Список расширяем через конфигурацию.
- **Field Source Binding (Привязка поля к источнику)**: соответствие «считываемое значение → источник» (основная зона или конкретная вкладка), определяющее, когда поле доступно для считывания.
- **Chest Type (Тип сундука)**: вид награды-сундука, заданный конфигурацией (на момент написания: базовый/коричневый, редкий/синий, легендарный/красный). Список расширяем без переработки модели.
- **Chest Tally (Учёт сундуков)**: количество сундуков по каждому типу — наблюдаемое в моменте и накопленное за забег.
- **Stage Run (Забег этапа)**: один завершённый проход этапа — ссылка на Stage, время прохождения (сек), прирост золота, прирост опыта, полученные сундуки по типам, момент завершения, связанный Hero Snapshot.
- **Metric Sample (Замер показателя)**: периодический срез наблюдаемых значений (золото, опыт, сундуки по типам, этап, время) с отметкой времени и признаком достоверности (читалось ли окно) — основа для вычисления темпов и трендов.
- **Stage Aggregate (Агрегат этапа)**: сводные показатели по этапу — средние/лучшие золото/час, опыт/час, время прохождения, темп сундуков по типам, число учтённых забегов.
- **Optimization Profile (Профиль оптимизации)**: выбранная пользователем цель (золото/час или опыт/час), определяющая ранжирование и рекомендацию.
- **Game Mechanics Config (Конфигурация игровых механик)**: декларативное описание учитываемых сущностей игры — типы сундуков, классы героя, акты/сложности/этапы и привязанные к ним области считывания. Позволяет добавлять новые элементы игры минимальными правками (см. FR-021).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: При запущенной игре помощник показывает живые золото/час и опыт/час для текущего этапа не позднее чем через 10 секунд после старта.
- **SC-002**: Отображаемые значения (золото, опыт, уровень, урон, этап) совпадают с показанными в игре в ≥98% наблюдений, когда значения читаемы.
- **SC-003**: После накопления истории минимум по двум этапам помощник выдаёт рекомендацию оптимального этапа, и она совпадает с этапом, имеющим лучший измеренный показатель по выбранной цели, в ≥95% случаев.
- **SC-004**: Вся накопленная история (вплоть до полной матрицы из 60 этапов) сохраняется и доступна после перезапуска помощника и перезагрузки ПК — потеря данных 0%.
- **SC-005**: Игрок находит лучший этап для фарма через экран сравнения менее чем за 30 секунд.
- **SC-006**: Виджет занимает не более ~15% площади экрана в компактном состоянии и по умолчанию не перекрывает критичные элементы игры.
- **SC-007**: При недоступности данных (окно перекрыто/свёрнуто/закрыто) помощник не записывает ни одной недостоверной точки в историю (0% «мусорных» записей) и не показывает ошибку — только статус ожидания.
- **SC-008**: После того как перекрытое/свёрнутое окно снова становится видимым, считывание возобновляется автоматически не позднее чем за 5 секунд, без действий пользователя.
- **SC-009**: При перемещении или изменении размера/масштаба окна игры (включая перенос на другой монитор) считывание продолжается без ручной перенастройки в ≥95% случаев.
- **SC-010**: Добавление нового элемента игровой механики (новый тип сундука, класс или вкладка) выполняется через конфигурацию без изменения архитектуры, и ранее накопленная история остаётся валидной (0% потери истории).
- **SC-011**: Помощник корректно определяет активную вкладку по её названию в ≥98% наблюдений, когда название читаемо, и не приписывает значения неверному источнику.
- **SC-012**: UI-тесты при повторных прогонах на одной версии игры дают одинаковый вердикт (детерминизм) — стабильность ≥98% на серии прогонов (флакийность близка к 0).
- **SC-013**: QA-харнесс успешно открывает и аудирует все 9 разделов (открытие + детекция активного) в ≥95% прогонов и выполняет **0** действий из запрещённого списка (никаких необратимых мутаций игрового состояния).
- **SC-014**: 100% автоматических кликов попадают в пределы границ целевого элемента; задержки между действиями варьируются в заданном диапазоне (человекоподобность), без фиксированного интервала.

## Assumptions

- **Платформа**: единственная целевая среда на данном этапе — Windows 11; один локальный игрок и один экземпляр игры.
- **Захват данных — визуальный (OCR)**: игра не предоставляет файл/API; значения распознаются с экрана. Области считывания привязаны к окну игры (а не к фиксированным координатам экрана), поэтому работают при любом положении/размере окна и любом разрешении/масштабе системы. Требуется первичная калибровка относительно окна; для считывания живых значений окно должно быть видимым (при перекрытии помощник ждёт).
- **Учёт сундуков**: считается количество сундуков по типам (сейчас 3: коричневый/синий/красный); список типов задаётся конфигурацией и расширяем.
- **Разделы игры (9)**: окно содержит основную зону и 9 именованных разделов; активный раздел определяется по названию. Источники нужных данных (по уточнению игрока 2026-05-31): **Hero** — текущее золото (вверху раздела) + инвентарь; **Status** — статистика выбранного героя (Level, EXP текущий/до уровня, Attack Damage и др.); **Portal** — выбор сложности/акта/этапа (идентификатор текущего этапа). Остальные разделы (Stash, Runes, Cube, Settings, Trade ship, Mail Box) в v1 не считываются. Значения привязаны к источникам (зона/раздел) и обновляются, когда соответствующий раздел открыт. Помощник не переключает разделы сам (observe-only) — обновление оппортунистическое, по действиям игрока. Подвкладки (Hero: Inventory/Composition; Stash) в текущем объёме не учитываются. (Полная карта — в data-model.md «Game UI Map».)
- **Механика выпадения сундуков**: коричневый (обычный) — с любого монстра на любом этапе; синий (редкий) — с босса в конце этапа; красный (легендарный) — с босса акта (этап «-10»). Это контекст для интерпретации темпов сундуков по этапам.
- **Отображение/учёт сундуков**: считываются из MainZone (точки под иконкой типа). Правило подсчёта (транзиентный счётчик, итог = сумма приростов) описано в Edge Cases «Сброс счётчика сундуков при открытии» — единый источник истины.
- **Следующая локация (MainZone)**: слева в основной зоне отображается следующая доступная локация (current+1 с переносом «-10 → следующий акт -1»); может служить дополнительным подтверждением текущего этапа. На максимально открытой локации не показывается.
- **Прогрессбар этапа (MainZone)**: в основной зоне отображается прогрессбар прохождения текущего этапа; в конце полоски появляется **босс этапа**, убийство которого = прохождение этапа. Это надёжный сигнал момента завершения этапа (FR-002) и сегментации забегов; босс этапа — источник шанса синего сундука (босс акта на «-10» — красного).
- **Отряд из 3 героев**: данные считываются для выбранного героя; настройка состава отряда в v1 не требуется.
- **Зависимость добычи от силы отряда (уточнение 2026-05-31)**: количество золота/опыта/сундуков зависит не только от этапа, но и от **уровней героев, надетых предметов, выставленной сложности и купленных рун**. Сложность — уже отдельное измерение этапа (Normal/Nightmare). Прочие факторы силы в v1 **не считываются полностью**: фиксируется лишь прокси — уровень и урон (Attack Damage) **выбранного** героя в `HeroSnapshot` каждого забега; предметы как статы, раздел Runes и герои 2–3 отряда вне объёма v1 (границы «Game UI Map»). Следствие: чтобы рекомендация отражала текущую силу, ранжирование ведётся по **свежему окну** недавних забегов (FR-008/FR-009), а сравнение наиболее валидно между забегами близкой силы; забеги при заметно меньшей силе помечаются «устаревшими». Полный учёт рун/предметов/всех героев — кандидат на будущее расширение.
- **Расширяемость механик**: новые сущности игры (типы сундуков, классы, акты/сложности/этапы) добавляются декларативно через конфигурацию игровых механик; архитектура не переписывается, история не теряется.
- **Частота опроса**: для idle-игры достаточно регулярного опроса с коротким интервалом (порядка единиц секунд); точное значение подбирается на этапе планирования из баланса точности и нагрузки.
- **Учитывается только активное время**: помощник измеряет показатели только когда он и игра работают одновременно; offline/idle-прирост без запущенного помощника в историю не попадает.
- **Цель оптимизации по умолчанию**: при отсутствии иного выбора пользователя ранжирование ведётся по золото/час, с возможностью переключения (уточняется в FR-009).
- **Android-приложение — вне объёма данной фичи**: реализуется в будущем; здесь обеспечивается только пригодность модели данных к удалённой выдаче (FR-020).
- **Структура контента игры** (по данным игрока, 2026-05-31, уточнено): 3 акта (Act 1/2/3) × 2 сложности (Normal, Nightmare) × 10 этапов = **60 этапов** (ранее в первичном описании ошибочно «3 сложности/90» — скорректировано); возможны будущие расширения (напр. новые сложности/акты).
- **Приватность**: все данные хранятся локально; внешняя передача отсутствует, пока пользователь явно не включит удалённый доступ.
- **UI-тестирование (QA)**: тесты прогоняются против **реально запущенной** игры (не моков). Инструмент — для нативной игры **FlaUI (UIA + нативный ввод) + визуальная локализация элементов (OCR/шаблоны, переиспользуя слой захвата) + инъекция кликов через SendInput**; Playwright неприменим (браузерный) — рассматривается только если игра окажется Electron с CDP (требует проверки). Харнесс — отдельный QA-проект, не часть поставки; продукт остаётся observe-only. Человекоподобный ввод: случайная точка в границах элемента, случайная задержка в заданном диапазоне, плавное перемещение курсора. Безопасные сценарии не нажимают кнопки, меняющие игровое состояние.

## Out of Scope

- Полноценное Android-приложение и удалённый сетевой доступ к статистике (только задел в модели данных).
- Любая автоматизация/вмешательство в игровой процесс (бот, авто-клики) в **поставляемом продукте** — продукт исключительно наблюдательно-аналитический (observe-only). Исключение: отдельный **QA-харнесс** инжектит ввод только в тестовом режиме для аудита интерфейса (FR-022…FR-027), не входит в поставку и ограничен безопасной навигацией.
- Учёт offline/idle-прироста, произошедшего без запущенного помощника.
- Подвкладки внутри разделов (учитываются только 9 разделов верхнего уровня в текущем объёме).
- Автоматическое переключение вкладок игрой/помощником (продукт observe-only).
- Многопользовательские/облачные сценарии, синхронизация между несколькими ПК.
